# 🟦 **接口字段规格（API 字段命名规范 · 终极总结）**

## 🟩 1. **统一使用小写 + 下划线（snake_case）**
这是后端接口最通用、最稳的风格。

示例：

- `plan_qty`
- `stockin_qty`
- `order_id`
- `created_at`

理由：

- JSON 不区分大小写，但 snake_case 最清晰  
- Python、Go、Rust、SQL 都天然支持 snake_case  
- 前端（TS/JS）也能轻松转换

---

## 🟧 2. **字段语义后缀与数据库保持一致**

接口字段与数据库字段保持同样的语义后缀：

| 后缀 | 含义 | 示例 |
|------|------|------|
| `_qty` | 实体数量 | `plan_qty` |
| `_cnt` | 次数/条数 | `error_cnt` |
| `_num` | 编号 | `order_num` |
| `_id` | 主键/外键 | `order_id` |
| `_rate` | 比率 | `pass_rate` |
| `_amt` | 金额 | `total_amt` |
| `_state` | 状态 | `qc_state` |
| `_status` | 状态（更完整） | `order_status` |
| `_time` | 时长 | `wait_time` |
| `_at` | 时间点 | `created_at` |
| `_ts` | 时间戳 | `start_ts` |

👉 **接口字段与数据库字段不必完全一致，但语义必须一致。**

---

## 🟥 3. **布尔字段必须以 `is_` / `has_` / `can_` 开头**

示例：

- `is_active`
- `has_error`
- `can_retry`

理由：

- 一眼就知道是布尔值  
- 前端不需要猜测类型  
- 避免 `0/1`、`true/false` 混乱

---

## 🟦 4. **时间字段必须明确类型**

| 类型 | 后缀 | 示例 |
|------|------|------|
| 时间点（字符串） | `_at` | `created_at` |
| 时间戳（数字） | `_ts` | `start_ts` |
| 时长（秒/分钟） | `_time` | `wait_time` |

避免出现：

- `time`  
- `date`  
- `timestamp`  

这种模糊字段。

---

## 🟩 5. **状态字段必须是 `_state` 或 `_status`**

- `_state` → 简短状态（如 “pending” / “done”）  
- `_status` → 更完整的业务状态（如 “WAITING_FOR_QC”）

示例：

- `qc_state`
- `order_status`

---

## 🟧 6. **列表字段必须是复数**

示例：

- `items`
- `orders`
- `records`
- `errors`

避免：

- `item_list`（冗余）
- `itemArray`（驼峰 + 类型信息）

---

## 🟥 7. **对象字段必须是名词**

示例：

```json
{
  "order": { ... },
  "customer": { ... },
  "production_status": { ... }
}
```

避免：

- `orderInfo`
- `customerData`

---

## 🟦 8. **接口返回结构必须稳定、统一**

推荐结构：

```json
{
  "code": 0,
  "msg": "success",
  "data": { ... }
}
```

错误示例：

- `status` 有时是数字，有时是字符串  
- `message` 有时是中文，有时是英文  
- `data` 有时是对象，有时是数组
