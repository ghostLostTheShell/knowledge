# 管理 Layers

在[管理服务](/docs/requirements-management/services/)页面中，你已经学习了如何创建依赖于某些服务才能运行的 effect，以及如何为 effect 提供这些服务。

然而，如果我们程序中的某个服务在构建时又依赖于其他服务，该怎么办？我们希望避免将这些实现细节泄露到服务接口中。

为了表示程序的“依赖图”并更有效地管理这些依赖关系，我们可以利用一个名为“Layer”的强大抽象。

Layer 充当**创建服务的构造器**，它允许我们在构建阶段而非服务层级管理依赖项。这种方法有助于保持服务接口的整洁和专注。

在深入细节之前，让我们先回顾一些核心概念：

| 概念 | 描述 |
| :--- | :--- |
| **服务 (service)** | 一个提供特定功能的可复用组件，用于应用程序的不同部分。 |
| **标签 (tag)** | 一个代表**服务**的唯一标识符，使 Effect 能够定位并使用该服务。 |
| **上下文 (context)** | 一个存储服务的集合，功能类似于以**标签 (tags)** 为键、**服务 (services)** 为值的映射 (Map)。 |
| **Layer (层)** | 一种用于构建**服务**的抽象，允许在构建阶段而非服务层级管理依赖项。 |

## 设计依赖图

让我们设想我们正在构建一个 Web 应用程序。对于一个需要管理配置、日志记录和数据库访问的应用程序，我们可以设想其依赖图可能如下所示：

- `Config` 服务提供应用程序配置。
- `Logger` 服务依赖于 `Config` 服务。
- `Database` 服务同时依赖于 `Config` 和 `Logger` 服务。

我们的目标是构建 `Database` 服务及其直接和间接依赖项。这意味着我们需要确保 `Config` 服务对 `Logger` 和 `Database` 都可用，然后将这些依赖项提供给 `Database` 服务。

## 避免依赖项泄露

在构建 `Database` 服务时，重要的是避免在 `Database` 接口中暴露对 `Config` 和 `Logger` 的依赖。

你可能会倾向于按照如下方式定义 `Database` 服务：

**示例**（在服务接口中泄露依赖项）

```ts 
import { Effect, Context } from "effect"

// 为 Config 服务声明一个 Tag
class Config extends Context.Tag("Config")<Config, {}>() {}

// 为 Logger 服务声明一个 Tag
class Logger extends Context.Tag("Logger")<Logger, {}>() {}

// 为 Database 服务声明一个 Tag
class Database extends Context.Tag("Database")<
  Database,
  {
    // ❌ 避免将 Config 和 Logger 作为需求项暴露出来
    readonly query: (
      sql: string
    ) => Effect.Effect<unknown, never, Config | Logger>
  }
>() {}
```

在这里，`Database` 服务的 `query` 函数同时需要 `Config` 和 `Logger`。这种设计泄露了实现细节，使 `Database` 服务察觉到了自身的依赖项，从而增加了测试的复杂性并导致难以进行模拟（mock）。

---
**保持服务接口简洁**
> 服务函数应避免直接请求依赖项。在实践中，服务操作的 `Requirements` 参数应当被设置为 `never`：

```ts
                         ┌─── No dependencies required
                         ▼
Effect<Success, Error, never>
```
---

为了说明这个问题，让我们创建一个 Database 服务的测试实例：

**Example** (带有泄露依赖项的测试实例创建过程`)

```ts
import { Effect, Context } from "effect"

// 为 Config 服务声明一个 Tag
class Config extends Context.Tag("Config")<Config, {}>() {}

// 为 Logger 服务声明一个 Tag
class Logger extends Context.Tag("Logger")<Logger, {}>() {}

// 为 Database 服务声明一个 Tag
class Database extends Context.Tag("Database")<
  Database,
  {
    readonly query: (
      sql: string
    ) => Effect.Effect<unknown, never, Config | Logger>
  }
>() {}

// 为 Database 服务声明一个测试实例
const DatabaseTest = Database.of({
  // 模拟一个简单的响应
  query: (sql: string) => Effect.succeed([])
})

import * as assert from "node:assert"

// 一个使用 Database 服务的测试
const test = Effect.gen(function* () {
  const database = yield* Database
  const result = yield* database.query("SELECT * FROM users")
  assert.deepStrictEqual(result, [])
})

//      ┌─── Effect<unknown, never, Config | Logger>
//      ▼
const incompleteTestSetup = test.pipe(
  // 尝试只提供 Database 服务，而不提供 Config 和 Logger
  Effect.provideService(Database, DatabaseTest)
)
```

由于 `Database` 服务接口直接包含了对 `Config` 和 `Logger` 的依赖，这强制任何测试设置都必须包含这些服务，即使它们与测试无关。这增加了不必要的复杂性，并导致难以编写简单、隔离的单元测试。

与其将依赖项直接绑定到 `Database` 服务接口，不如在构建阶段管理这些依赖。

我们可以使用 **Layer** 来正确构建 `Database` 服务并管理其依赖项，而不会将细节泄露到接口中。

---
**Use Layers for Dependencie**

> 当一个服务拥有自己的需求项时，最好将实现细节分离到层（Layer）中。Layer 充当**创建服务的构造器**，允许我们在构建层级而非服务层级处理依赖项。
---


## 创建 Layer

`Layer` 类型的结构如下：

```ts
        ┌─── The service to be created
        │                ┌─── The possible error
        │                │      ┌─── The required dependencies
        ▼                ▼      ▼
Layer<RequirementsOut, Error, RequirementsIn>
```
一个 `Layer` 代表了构建 `RequirementsOut`（服务）的一个蓝图。它需要 `RequirementsIn`（依赖项）作为输入，并且在构建过程中可能会产生类型为 `Error` 的错误。

| 参数 | 描述 |
| :--- | :--- |
| `RequirementsOut` | 要创建的服务或资源。 |
| `Error` | 在构建服务过程中可能发生的错误类型。 |
| `RequirementsIn` | 构建服务所需的依赖项。 |


通过使用 Layer，你可以更好地组织服务，确保其依赖关系清晰定义并与实现细节分离。

为简单起见，我们假设在构建值的过程中不会遇到任何错误（即 `Error = never`）。

现在，让我们确定实现我们的依赖图需要多少个 Layer：

| Layer | 依赖项 | 类型 |
| :--- | :--- | :--- |
| `ConfigLive` | `Config` 服务不依赖任何其他服务 | `Layer<Config>` |
| `LoggerLive` | `Logger` 服务依赖于 `Config` 服务 | `Layer<Logger, never, Config>` |
| `DatabaseLive` | `Database` 服务依赖于 `Config` 和 `Logger` | `Layer<Database, never, Config \| Logger>` |

---
**命名约定**
> 当为特定服务的 `Layer` 命名时，通常的约定是为“生产”实现添加 `Live` 后缀，为“测试”实现添加 `Test` 后缀。例如，对于 `Database` 服务，`DatabaseLive` 是你在应用程序中提供的 Layer，而 `DatabaseTest` 是你在测试中提供的 Layer。
---

当一个服务有多个依赖项时，它们被表示为一个**联合类型 (union type)**。在我们的例子中，`Database` 服务同时依赖于 `Config` 和 `Logger` 服务。因此，`DatabaseLive` 层的类型将是：

```ts
Layer<Database, never, Config | Logger>
```

### Config

`Config` 服务不依赖于任何其他服务，因此 `ConfigLive` 将是最容易实现的 Layer。就像在[管理服务](/docs/requirements-management/services/)页面中一样，我们必须为服务创建一个 Tag。由于该服务没有任何依赖项，我们可以直接使用 `Layer.succeed` 构造函数来创建这个 Layer：
```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(
  Config,
  Config.of({
    getConfig: Effect.succeed({
      logLevel: "INFO",
      connection: "mysql://username:password@hostname:port/database_name"
    })
  })
)
```

查看 `ConfigLive` 的类型，我们可以观察到：

- `RequirementsOut` 是 `Config`，表示构建该层将产生一个 `Config` 服务
- `Error` 是 `never`，表示构建层不会失败
- `RequirementsIn` 是 `never`，表示该层没有依赖项

请注意，为了构建 `ConfigLive` 我们使用了 `Config.of` 构造器。然而，这仅仅是一个用于确保实现时正确类型推断的辅助函数。跳过此辅助函数，直接将实现构建为一个简单对象也是可以的：

```ts 
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})
```

### Logger

现在我们可以进入 `Logger` 服务的实现，该服务依赖于 `Config` 服务来检索某些配置。

就像我们在[管理服务](/docs/requirements-management/services/#using-the-service)页面中所做的那样，我们可以 yield `Config` 标签来从上下文中“提取”该服务。

鉴于使用 `Config` 标签是一个带有 effect 的操作，我们使用 `Layer.effect` 来从生成的 effect 中创建一个 Layer。

```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})

// Declaring a tag for the Logger service
class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

// Layer<Logger, never, Config>
const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)
```

查看 `LoggerLive` 的类型：

```ts
Layer<Logger, never, Config>
```

我们可以观察到：

- `RequirementsOut` 是 `Logger`
- `Error` 是 `never`，表示构建该层不会失败
- `RequirementsIn` 是 `Config`，表示该层具有一个需求项（dependency）

### Database

最后，我们可以使用 `Config` 和 `Logger` 服务来实现 `Database` 服务。

```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})

// Declaring a tag for the Logger service
class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

// Layer<Logger, never, Config>
const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)

// Declaring a tag for the Database service
class Database extends Context.Tag("Database")<
  Database,
  { readonly query: (sql: string) => Effect.Effect<unknown> }
>() {}

// Layer<Database, never, Config | Logger>
const DatabaseLive = Layer.effect(
  Database,
  Effect.gen(function* () {
    const config = yield* Config
    const logger = yield* Logger
    return {
      query: (sql: string) =>
        Effect.gen(function* () {
          yield* logger.log(`Executing query: ${sql}`)
          const { connection } = yield* config.getConfig
          return { result: `Results from ${connection}` }
        })
    }
  })
)
```

查看 `DatabaseLive` 的类型：

```ts 
Layer<Database, never, Config | Logger>
```

我们可以观察到，`RequirementsIn` 类型是 `Config | Logger`，也就是说，`Database` 服务需要同时具备 `Config` 和 `Logger` 服务。


## 组合 Layer

Layer 主要可以通过两种方式进行组合：**合并 (Merging)** 和 **复合 (Composing)**。

### 合并 Layer

可以使用 `Layer.merge` 函数将 Layer 组合到一起进行合并：

```ts
import { Layer } from "effect"

declare const layer1: Layer.Layer<"Out1", never, "In1">
declare const layer2: Layer.Layer<"Out2", never, "In2">

// Layer<"Out1" | "Out2", never, "In1" | "In2">
const merging = Layer.merge(layer1, layer2)
```

当我们合并两个 Layer 时，生成的新 Layer：

- 需要两者各自需要的所有服务（即 `"In1" | "In2"`）。
- 产生两者各自产生的所有服务（即 `"Out1" | "Out2"`）。

例如，在上述 Web 应用中，我们可以将 `ConfigLive` 和 `LoggerLive` 层合并为一个单独的 `AppConfigLive` 层。该层将保留两个层的需求项（`never | Config = Config`），并产生两个层的输出（`Config | Logger`）：

```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})

// Declaring a tag for the Logger service
class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

// Layer<Logger, never, Config>
const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)

// Layer<Config | Logger, never, Config>
const AppConfigLive = Layer.merge(ConfigLive, LoggerLive)
```

### 复合 Layer

可以使用 `Layer.provide` 函数对 Layer 进行复合：

```ts twoslash
import { Layer } from "effect"

declare const inner: Layer.Layer<"OutInner", never, "InInner">
declare const outer: Layer.Layer<"InInner", never, "InOuter">

// Layer<"OutInner", never, "InOuter">
const composition = Layer.provide(inner, outer)
```

Layer 的顺序复合意味着：一个层的输出被提供给内层作为输入，从而产生一个具有外层需求项和内层输出的单一层。

现在我们可以将 `AppConfigLive` 层与 `DatabaseLive` 层进行复合：

```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

// Layer<Config, never, never>
const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})

// Declaring a tag for the Logger service
class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

// Layer<Logger, never, Config>
const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)

// Declaring a tag for the Database service
class Database extends Context.Tag("Database")<
  Database,
  { readonly query: (sql: string) => Effect.Effect<unknown> }
>() {}

// Layer<Database, never, Config | Logger>
const DatabaseLive = Layer.effect(
  Database,
  Effect.gen(function* () {
    const config = yield* Config
    const logger = yield* Logger
    return {
      query: (sql: string) =>
        Effect.gen(function* () {
          yield* logger.log(`Executing query: ${sql}`)
          const { connection } = yield* config.getConfig
          return { result: `Results from ${connection}` }
        })
    }
  })
)

// Layer<Config | Logger, never, Config>
const AppConfigLive = Layer.merge(ConfigLive, LoggerLive)

// Layer<Database, never, never>
const MainLive = DatabaseLive.pipe(
  // provides the config and logger to the database
  Layer.provide(AppConfigLive),
  // provides the config to AppConfigLive
  Layer.provide(ConfigLive)
)
```

我们获得了一个产生 `Database` 服务的 `MainLive` 层：

```ts showLineNumbers=false
Layer<Database, never, never>
```

这个层是为我们应用程序完全解析后的 Layer。

### 合并与复合 Layer

假设我们希望 `MainLive` 层同时返回 `Config` 和 `Database` 服务。我们可以通过 `Layer.provideMerge` 来实现：

```ts
import { Effect, Context, Layer } from "effect"

// Declaring a tag for the Config service
class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string

  }

const ConfigLive = Layer.succeed(Config, {

    connection: "mysql://username:password@hostname:port/database_name"
  })
})

// Declaring a tag for the Logger service
class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)

// Declaring a tag for the Database service
class Database extends Context.Tag("Database")<
  Database,
  { readonly query: (sql: string) => Effect.Effect<unknown> }
>() {}

const DatabaseLive = Layer.effect(
  Database,
  Effect.gen(function* () {
    const config = yield* Config
    const logger = yield* Logger
    return {
      query: (sql: string) =>
        Effect.gen(function* () {
          yield* logger.log(`Executing query: ${sql}`)

  Layer.provideMerge(ConfigLive)

```

## 将 Layer 提供给 Effect

现在我们已经为应用程序组装好了完全解析的 `MainLive`，我们可以使用 `Effect.provide` 将其提供给我们的程序，以满足程序的需求：

```ts
import { Effect, Context, Layer } from "effect"

class Config extends Context.Tag("Config")<
  Config,
  {
    readonly getConfig: Effect.Effect<{
      readonly logLevel: string
      readonly connection: string
    }>
  }
>() {}

const ConfigLive = Layer.succeed(Config, {
  getConfig: Effect.succeed({
    logLevel: "INFO",
    connection: "mysql://username:password@hostname:port/database_name"
  })
})

class Logger extends Context.Tag("Logger")<
  Logger,
  { readonly log: (message: string) => Effect.Effect<void> }
>() {}

const LoggerLive = Layer.effect(
  Logger,
  Effect.gen(function* () {
    const config = yield* Config
    return {
      log: (message) =>
        Effect.gen(function* () {
          const { logLevel } = yield* config.getConfig
          console.log(`[${logLevel}] ${message}`)
        })
    }
  })
)

class Database extends Context.Tag("Database")<
  Database,
  { readonly query: (sql: string) => Effect.Effect<unknown> }
>() {}

const DatabaseLive = Layer.effect(
  Database,
  Effect.gen(function* () {
    const config = yield* Config
    const logger = yield* Logger
    return {
      query: (sql: string) =>
        Effect.gen(function* () {
          yield* logger.log(`Executing query: ${sql}`)
          const { connection } = yield* config.getConfig
          return { result: `Results from ${connection}` }
        })
    }
  })
)

const AppConfigLive = Layer.merge(ConfigLive, LoggerLive)

const MainLive = DatabaseLive.pipe(
  Layer.provide(AppConfigLive),
  Layer.provide(ConfigLive)
)

//      ┌─── Effect<unknown, never, Database>
//      ▼
const program = Effect.gen(function* () {
  const database = yield* Database
  const result = yield* database.query("SELECT * FROM users")
  return result
})

//      ┌─── Effect<unknown, never, never>
//      ▼
const runnable = Effect.provide(program, MainLive)

Effect.runPromise(runnable).then(console.log)
/*
Output:
[INFO] Executing query: SELECT * FROM users
{
  result: 'Results from mysql://username:password@hostname:port/database_name'
}
*/
```
请注意，`runnable` 的需求项类型是 `never`，这表示该程序运行不再需要任何额外的服务。

## 将 Layer 转换为 Effect

有时你的整个应用程序可能就是一个 Layer，例如一个 HTTP 服务器。你可以使用 `Layer.launch` 将该层转换为一个 effect。它会构建该层并使其保持运行，直到被中断。

**示例**（启动一个 HTTP 服务器层）

```ts 
import { Console, Context, Effect, Layer } from "effect"

class HTTPServer extends Context.Tag("HTTPServer")<HTTPServer, void>() {}

// Simulating an HTTP server
const server = Layer.effect(
  HTTPServer,
  // Log a message to simulate a server starting
  Console.log("Listening on http://localhost:3000")
)

// Converts the layer to an effect and runs it
Effect.runFork(Layer.launch(server))
/*
Output:
Listening on http://localhost:3000
...
*/
```

## Tapping (分流监听)

`Layer.tap` 和 `Layer.tapError` 函数允许你在 Layer 成功或失败时执行额外的 effect。这些操作不会修改 Layer 的签名（类型定义），但对于在构建 Layer 过程中记录日志或执行副作用非常有用。

- `Layer.tap`：在 Layer 成功获取（实例化）时执行指定的 effect。
- `Layer.tapError`：在 Layer 获取失败时执行指定的 effect。

**示例**（在获取 Layer 过程中记录成功与失败日志）

```ts twoslash
import { Config, Context, Effect, Layer, Console } from "effect"

class HTTPServer extends Context.Tag("HTTPServer")<HTTPServer, void>() {}

// 模拟一个 HTTP 服务器
const server = Layer.effect(
  HTTPServer,
  Effect.gen(function* () {
    const host = yield* Config.string("HOST")
    console.log(`正在监听 http://localhost:${host}`)
  })
).pipe(
  // 如果获取 Layer 成功，则记录一条消息
  Layer.tap((ctx) =>
    Console.log(`获取 Layer 成功，上下文内容为：\n${ctx}`)
  ),
  // 如果获取 Layer 失败，则记录一条消息
  Layer.tapError((err) =>
    Console.log(`获取 Layer 失败，原因为：\n${err}`)
  )
)

Effect.runFork(Layer.launch(server))
/*
输出：
获取 Layer 失败，原因为：
(Missing data at HOST: "Expected HOST to exist in the process context")
*/
```

## 错误处理

在构建 Layer 时，处理潜在的错误非常重要。Effect 库提供了诸如 `Layer.catchAll` 和 `Layer.orElse` 等工具，用于管理错误并在失败时定义备选（fallback）Layer。

### catchAll

`Layer.catchAll` 函数允许你通过指定一个备选 Layer，从构建 Layer 过程中的错误中恢复。这在处理特定错误情况以及确保应用程序能够以替代方案继续运行时非常有用。

**示例**（从构建 Layer 过程中的错误恢复）

```ts twoslash
import { Config, Context, Effect, Layer } from "effect"

class HTTPServer extends Context.Tag("HTTPServer")<HTTPServer, void>() {}

// Simulating an HTTP server
const server = Layer.effect(
  HTTPServer,
  Effect.gen(function* () {
    const host = yield* Config.string("HOST")
    console.log(`Listening on http://localhost:${host}`)
  })
).pipe(
  // Recover from errors during layer construction
  Layer.catchAll((configError) =>
    Layer.effect(
      HTTPServer,
      Effect.gen(function* () {
        console.log(`Recovering from error:\n${configError}`)
        console.log(`Listening on http://localhost:3000`)
      })
    )
  )
)

Effect.runFork(Layer.launch(server))
/*
Output:
Recovering from error:
(Missing data at HOST: "Expected HOST to exist in the process context")
Listening on http://localhost:3000
...
*/
```


### orElse

`Layer.orElse` 函数提供了一种更简单的方法，在初始 Layer 失败时回退到另一个备选 Layer。与 `Layer.catchAll` 不同，它不接收错误作为输入。当你只需要提供一个默认 Layer 而不需要针对特定错误做出反应时，请使用此函数。

**示例**（回退到备选 Layer）

```ts twoslash
import { Config, Context, Effect, Layer } from "effect"

class Database extends Context.Tag("Database")<Database, void>() {}

// 模拟数据库连接
const postgresDatabaseLayer = Layer.effect(
  Database,
  Effect.gen(function* () {
    const databaseConnectionString = yield* Config.string(
      "CONNECTION_STRING"
    )
    console.log(
      `正在连接数据库，连接字符串为：${databaseConnectionString}`
    )
  })
)

// 模拟内存数据库连接
const inMemoryDatabaseLayer = Layer.effect(
  Database,
  Effect.gen(function* () {
    console.log(`正在连接内存数据库`)
  })
)

// 如果 PostgreSQL 连接失败，则回退到内存数据库
const database = postgresDatabaseLayer.pipe(
  Layer.orElse(() => inMemoryDatabaseLayer)
)

Effect.runFork(Layer.launch(database))
/*
输出：
正在连接内存数据库
...
*/
```

## 使用 Effect.Service 简化服务定义

`Effect.Service` API 提供了一种单步定义服务的方式，包括其 Tag 和 Layer。它还允许预先指定依赖项，使服务构建更加直观。

### 定义带有依赖项的服务

以下示例定义了一个依赖于文件系统的 `Cache` 服务。

**示例**（定义 Cache 服务）

```ts twoslash
import { FileSystem } from "@effect/platform"
import { NodeFileSystem } from "@effect/platform-node"
import { Effect } from "effect"

// 定义 Cache 服务
class Cache extends Effect.Service<Cache>()("app/Cache", {
  // 定义如何创建该服务
  effect: Effect.gen(function* () {
    const fs = yield* FileSystem.FileSystem
    const lookup = (key: string) => fs.readFileString(`cache/${key}`)
    return { lookup } as const
  }),
  // 指定依赖项
  dependencies: [NodeFileSystem.layer]
}) {}
```

### 使用生成的 Layer

`Effect.Service` API 会自动为该服务生成 Layer。

| Layer | 描述 |
| :--- | :--- |
| `Cache.Default` | 提供已包含其所有依赖项的 `Cache` 服务。 |
| `Cache.DefaultWithoutDependencies` | 提供 `Cache` 服务，但需要另行提供其依赖项。 |

```ts twoslash collapse={6-13}
import { FileSystem } from "@effect/platform"
import { NodeFileSystem } from "@effect/platform-node"
import { Effect } from "effect"

// 定义 Cache 服务
class Cache extends Effect.Service<Cache>()("app/Cache", {
  effect: Effect.gen(function* () {
    const fs = yield* FileSystem.FileSystem
    const lookup = (key: string) => fs.readFileString(`cache/${key}`)
    return { lookup } as const
  }),
  dependencies: [NodeFileSystem.layer]
}) {}

// 包含所有必需依赖项的 Layer
//
//      ┌─── Layer<Cache>
//      ▼
const layer = Cache.Default

// 不含依赖项的 Layer，需要从外部提供依赖项
//
//      ┌─── Layer.Layer<Cache, never, FileSystem>
//      ▼
const layerNoDeps = Cache.DefaultWithoutDependencies
```

### 访问服务

使用 `Effect.Service` 创建的服务可以像任何其他 Effect 服务一样被访问。

**示例**（访问 Cache 服务）

```ts twoslash collapse={6-13}
import { FileSystem } from "@effect/platform"
import { NodeFileSystem } from "@effect/platform-node"
import { Effect, Console } from "effect"

// 定义 Cache 服务
class Cache extends Effect.Service<Cache>()("app/Cache", {
  effect: Effect.gen(function* () {
    const fs = yield* FileSystem.FileSystem
    const lookup = (key: string) => fs.readFileString(`cache/${key}`)
    return { lookup } as const
  }),
  dependencies: [NodeFileSystem.layer]
}) {}

// 访问 Cache 服务
const program = Effect.gen(function* () {
  const cache = yield* Cache
  const data = yield* cache.lookup("my-key")
  console.log(data)
}).pipe(Effect.catchAllCause((cause) => Console.log(cause)))

const runnable = program.pipe(Effect.provide(Cache.Default))

Effect.runFork(runnable)
/*
输出：
{
  _id: 'Cause',
  _tag: 'Fail',
  failure: {
    _tag: 'SystemError',
    reason: 'NotFound',
    module: 'FileSystem',
    method: 'readFile',
    pathOrDescriptor: 'cache/my-key',
    syscall: 'open',
    message: "ENOENT: no such file or directory, open 'cache/my-key'",
    [Symbol(@effect/platform/Error/PlatformErrorTypeId)]: Symbol(@effect/platform/Error/PlatformErrorTypeId)
  }
}
*/
```

由于此示例使用了 `Cache.Default`，它会与真实的文件系统进行交互。如果文件不存在，则会导致错误。

### 注入测试依赖项

为了在不依赖真实文件系统的情况下测试程序，我们可以使用 `Cache.DefaultWithoutDependencies` 层并注入一个测试用的文件系统。

**示例**（使用测试文件系统）

```ts twoslash collapse={6-13,16-20}
import { FileSystem } from "@effect/platform"
import { NodeFileSystem } from "@effect/platform-node"
import { Effect, Console } from "effect"

// 定义 Cache 服务
class Cache extends Effect.Service<Cache>()("app/Cache", {
  effect: Effect.gen(function* () {
    const fs = yield* FileSystem.FileSystem
    const lookup = (key: string) => fs.readFileString(`cache/${key}`)
    return { lookup } as const
  }),
  dependencies: [NodeFileSystem.layer]
}) {}

// 访问 Cache 服务
const program = Effect.gen(function* () {
  const cache = yield* Cache
  const data = yield* cache.lookup("my-key")
  console.log(data)
}).pipe(Effect.catchAllCause((cause) => Console.log(cause)))

// 创建一个始终返回固定值的测试文件系统
const FileSystemTest = FileSystem.layerNoop({
  readFileString: () => Effect.succeed("File Content...")
})

const runnable = program.pipe(
  Effect.provide(Cache.DefaultWithoutDependencies),
  // 提供模拟（mock）的文件系统
  Effect.provide(FileSystemTest)
)

Effect.runFork(runnable)
// 输出: File Content...
```

### 直接模拟服务

或者，你也可以直接模拟 `Cache` 服务本身，而不是替换其依赖项。

**示例**（模拟 Cache 服务）

```ts twoslash collapse={6-13,16-20}
import { FileSystem } from "@effect/platform"
import { NodeFileSystem } from "@effect/platform-node"
import { Effect, Console } from "effect"

// 定义一个 Cache 服务
class Cache extends Effect.Service<Cache>()("app/Cache", {
  effect: Effect.gen(function* () {
    const fs = yield* FileSystem.FileSystem
    const lookup = (key: string) => fs.readFileString(`cache/${key}`)
    return { lookup } as const
  }),
  dependencies: [NodeFileSystem.layer]
}) {}

// 访问 Cache 服务
const program = Effect.gen(function* () {
  const cache = yield* Cache
  const data = yield* cache.lookup("my-key")
  console.log(data)
}).pipe(Effect.catchAllCause((cause) => Console.log(cause)))

// 创建 Cache 的模拟实现
const cache = new Cache({
  lookup: () => Effect.succeed("Cache Content...")
})

// 提供模拟的 Cache 服务
const runnable = program.pipe(Effect.provideService(Cache, cache))

Effect.runFork(runnable)
// 输出: Cache Content...
```

### 定义服务的其他方式

`Effect.Service` API 支持多种定义服务的方式：

| 方法 | 描述 |
| :--- | :--- |
| `succeed` | 提供服务的静态实现。 |
| `sync` | 使用同步构造函数定义服务。 |
| `effect` | 使用带有 effect 的构造函数定义服务。 |
| `scoped` | 创建具有生命周期管理的服务。 |

**示例**（定义具有静态实现的服务）

这是定义服务最简单的方式。当你想要为服务提供一个常量值时，这非常有用。

```ts twoslash
import { Effect } from "effect"

class MagicNumber extends Effect.Service<MagicNumber>()("MagicNumber", {
  succeed: { value: 42 }
}) {}

//      ┌─── Effect<void, never, MagicNumber>
//      ▼
const program = Effect.gen(function* () {
  const magicNumber = yield* MagicNumber
  console.log(`幻数是 ${magicNumber.value}`)
})

Effect.runPromise(program.pipe(Effect.provide(MagicNumber.Default)))
// 幻数是 42
```

**示例**（使用同步构造函数定义服务）

```ts twoslash
import { Effect, Random } from "effect"

class Sync extends Effect.Service<Sync>()("Sync", {
  sync: () => ({
    next: Random.nextInt
  })
}) {}

//      ┌─── Effect<void, never, Sync>
//      ▼
const program = Effect.gen(function* () {
  const sync = yield* Sync
  const n = yield* sync.next
  console.log(`数字是 ${n}`)
})

Effect.runPromise(program.pipe(Effect.provide(Sync.Default)))
// 示例输出：数字是 3858843290019673
```

**示例**（具有生命周期控制的服务管理）

```ts twoslash
import { Effect, Console } from "effect"

class Scoped extends Effect.Service<Scoped>()("Scoped", {
  scoped: Effect.gen(function* () {
    // 获取资源并确保其被正确释放
    const resource = yield* Effect.acquireRelease(
      Console.log("正在获取...").pipe(Effect.as("foo")),
      () => Console.log("正在释放...")
    )
    // 注册一个在 effect 完成时运行的终结器 (finalizer)
    yield* Effect.addFinalizer(() => Console.log("正在关闭"))
    return { resource }
  })
}) {}

//      ┌─── Effect<void, never, Scoped>
//      ▼
const program = Effect.gen(function* () {
  const resource = (yield* Scoped).resource
  console.log(`资源是 ${resource}`)
})

Effect.runPromise(
  program.pipe(
    Effect.provide(
      //       ┌─── Layer<Scoped, never, never>
      //       ▼
      Scoped.Default
    )
  )
)
/*
输出：
正在获取...
资源是 foo
正在关闭
正在释放...
*/
```

`Scoped.Default` 层不需要 `Scope` 作为依赖项，因为 `Scoped` 自身管理其生命周期。

### 启用直接方法访问

通过设置 `accessors: true`，你可以直接使用服务标签（Tag）调用服务方法，而无需先提取服务实例。

**示例**（定义具有直接方法访问权的服务）

```ts 
import { Effect, Random } from "effect"

class Sync extends Effect.Service<Sync>()("Sync", {
  sync: () => ({
    next: Random.nextInt
  }),
  accessors: true // 允许通过 Tag 直接访问方法
}) {}

const program = Effect.gen(function* () {
  // const sync = yield* Sync
  // const n = yield* sync.next
  const n = yield* Sync.next // 无需先提取服务实例
  console.log(`数字是 ${n}`)
})

Effect.runPromise(program.pipe(Effect.provide(Sync.Default)))
// 示例输出：数字是 3858843290019673
```
----
**直接方法访问的局限性**
> 直接方法访问不支持泛型方法。

### Effect.Service 与 Context.Tag 的对比

`Effect.Service` 和 `Context.Tag` 都是 Effect 生态系统中建模服务的方式。它们用途相似，但针对不同的使用场景。

| 特性 | Effect.Service | Context.Tag |
| :--- | :--- | :--- |
| **Tag 创建** | 自动为你生成（类名即作为 Tag） | 你需要手动声明 Tag |
| **默认实现** | **必须提供** - 通过内联方式（`effect`, `sync` 等） | **可选** - 可以在之后提供 |
| **现成的 Layer (`.Default`, ...)** | 自动生成 | 需要你自己构建 Layer |
| **最适用场景** | 具有明确运行时实现的应用代码 | 库代码或动态作用域的值 |
| **无合理默认实现时** | 不太理想；你仍必须造一个出来 | 首选 |

**核心要点**

- **更少的样板代码**：`Effect.Service` 是对 `Context.Tag` 及其配套 Layer 和辅助函数的语法糖。
- **必须有默认实现**：
  继承自 `Effect.Service` 的类必须声明内置构造函数（`effect`、`sync`、`succeed` 或 `scoped`）中的**一个**。这个基础实现会成为 `MyService.Default` 的一部分，因此任何导入该服务的代码都可以在不提供额外 Layer 的情况下运行。
  这对于存在合理运行时实现（如日志记录、HTTP 客户端、真实数据库等）的应用级服务非常方便。
  如果你的服务本质上是上下文相关的（例如：针对每个请求的数据库句柄），或者你正在编写一个不应假设具体实现的库，请首选 `Context.Tag`：你只发布 Tag，让调用者根据其环境提供合适的 Layer。
- **类本身即是标签**：当你使用 `extends Effect.Service` 创建类时，类构造函数本身充当 Tag。在组装 Layer 时，你可以通过为该类提供一个值来提供备选实现：

  ```ts
  const mock = new MyService({
    /* 模拟的方法 */
  })
  program.pipe(Effect.provideService(MyService, mock))
  ```
