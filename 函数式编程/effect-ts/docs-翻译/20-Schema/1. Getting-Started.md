你可以从 `effect/Schema` 模块中导入必要的类型和函数：

**示例**（命名空间导入）

```ts 
import * as Schema from "effect/Schema"
```

**示例**（命名导入）

```ts 
import { Schema } from "effect"
```
## 定义 Schema

定义 `Schema` 的一种常用方法是利用 `Struct` 构造函数。该构造函数允许你创建一个描述具有特定属性的对象的新 Schema。对象中的每个属性都由其自身的 Schema 定义，这指定了数据类型和任何验证规则。

**示例**（定义一个简单的对象 Schema）

这个 `Person` Schema 描述了一个具有 `name`（字符串）和 `age`（数字）属性的对象：

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})
```

## 提取推断类型

### Type

一旦你定义了一个 Schema (`Schema<Type, Encoded, Context>`)，你可以通过两种方式提取推断出的类型 `Type`：

1. 使用 `Schema.Type` 工具
2. 直接访问 Schema 上的 `Type` 字段

**示例**（提取推断类型）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 1. 使用 Schema.Type 工具
type Person = Schema.Schema.Type<typeof Person>

// 2. 直接访问 Type 字段
type Person2 = typeof Person.Type
```

生成的类型如下所示：

```ts showLineNumbers=false
type Person = {
  readonly name: string
  readonly age: number
}
```

或者，你可以使用 `interface` 关键字来提取 `Person` 类型，在某些情况下，这可以提高代码的可读性和性能。

**示例**（使用接口提取类型）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

interface Person extends Schema.Schema.Type<typeof Person> {}
```

这两种方法产生的结果相同，但使用接口具有性能优势和更好的可读性等优点。

### Encoded

在 `Schema<Type, Encoded, Context>` 中，`Encoded` 类型可能与 `Type` 类型不同，它代表了数据被编码后的格式。你可以通过以下两种方式提取 `Encoded` 类型：

1. 使用 `Schema.Encoded` 工具
2. 直接访问 Schema 上的 `Encoded` 字段

**示例**（提取编码后的类型）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  // 一个将字符串解码为数字的 schema
  age: Schema.NumberFromString
})

// 1. 使用 Schema.Encoded 工具
type PersonEncoded = Schema.Schema.Encoded<typeof Person>

// 2. 直接访问 Encoded 字段
type PersonEncoded2 = typeof Person.Encoded
```

生成的类型如下：

```ts showLineNumbers=false
type PersonEncoded = {
  readonly name: string
  readonly age: string
}
```

请注意，在 Schema 的 `Encoded` 类型中 `age` 是 `string` 类型，而在 `Type` 类型中则是 `number` 类型。

或者，你也可以使用 `interface` 关键字定义 `PersonEncoded` 类型，这可以增强可读性并在某些情况下提升性能。

**示例**（使用接口提取编码后的类型）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  // 一个将字符串解码为数字的 schema
  age: Schema.NumberFromString
})

interface PersonEncoded extends Schema.Schema.Encoded<typeof Person> {}
```

这两种方法产生的结果相同，但使用接口具有性能优势和更好的可读性等优点。

### Context

在 `Schema<Type, Encoded, Context>` 中，`Context` 类型表示 Schema 在执行编码或解码时所需的任何外部数据或依赖项。你可以通过以下两种方式提取推断出的 `Context` 类型：

1. 使用 `Schema.Context` 工具。
2. 直接访问 Schema 上的 `Context` 字段。

**示例**（提取上下文类型）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 1. 使用 Schema.Context 工具
type PersonContext = Schema.Schema.Context<typeof Person>

// 2. 直接访问 Context 字段
type PersonContext2 = typeof Person.Context
```

### 带有不透明类型的 Schema

在定义 Schema 时，你可能希望创建一个带有不透明类型（Opaque Type）的 Schema。当你想要隐藏 Schema 的内部结构并仅暴露其类型时，这非常有用。

**示例**（创建不透明 Schema）

要创建一个带有不透明类型的 Schema，可以使用以下重新声明 Schema 的技巧：

```ts twoslash
import { Schema } from "effect"

// 定义 Schema 结构
const _Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 声明类型接口使其成为不透明类型
interface Person extends Schema.Schema.Type<typeof _Person> {}

// 将 Schema 重新声明为不透明
const Person: Schema.Schema<Person> = _Person
```

或者，你可以使用类 API（详情请参阅 [类 API](/docs/schema/classes/) 部分）。

请注意，当定义的 Schema 中 `Type` 与 `Encoded` 不同时，上述技巧会变得更加复杂。

**示例**（Type 与 Encoded 不同时的不透明 Schema）

```ts twoslash "NumberFromString"
import { Schema } from "effect"

// 定义 Schema 结构，其中有一个字段
// 将字符串解码为数字
const _Person = Schema.Struct({
  name: Schema.String,
  age: Schema.NumberFromString
})

// 为不透明 Schema 创建 `Type` 接口
interface Person extends Schema.Schema.Type<typeof _Person> {}

// 为不透明 Schema 创建 `Encoded` 接口
interface PersonEncoded extends Schema.Schema.Encoded<typeof _Person> {}

// 使用不透明的 Type 和 Encoded 重新声明 Schema
const Person: Schema.Schema<Person, PersonEncoded> = _Person
```

在这种情况下，`"age"` 字段在 Schema 的 `Encoded` 类型中是 `string` 类型，而在 `Type` 类型中是 `number` 类型。因此，我们需要定义**两个**接口（`PersonEncoded` 和 `Person`），并同时使用它们来重新声明我们最终的 `Person` Schema。

## 默认 Readonly 类型

需要注意的是，默认情况下，`effect/Schema` 导出的绝大多数构造函数返回的都是 `readonly`（只读）类型。

**示例**（Schema 中的只读类型）

例如，在下面的 `Person` Schema 中：

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})
```

推断出的结果 `Type` 将会是：

```ts showLineNumbers=false "readonly"
{
  readonly name: string;
  readonly age: number;
}
```

# 解码 (Decoding)

在 TypeScript 中处理未知数据类型时，将其解码为已知结构可能具有挑战性。幸运的是，`effect/Schema` 提供了几个函数来辅助这一过程。让我们来看看如何使用这些函数解码未知值。

| API | 描述 |
| :--- | :--- |
| `decodeUnknownSync` | 同步解码一个值，如果解析失败则抛出错误。 |
| `decodeUnknownOption` | 解码一个值并返回 [Option](/docs/data-types/option/) 类型。 |
| `decodeUnknownEither` | 解码一个值并返回 [Either](/docs/data-types/either/) 类型。 |
| `decodeUnknownPromise` | 解码一个值并返回 `Promise`。 |
| `decodeUnknown` | 解码一个值并返回 [Effect](/docs/getting-started/the-effect-type/)。 |

### decodeUnknownSync

当你想要解析一个值，且如果解析失败则希望立即抛出错误时，`Schema.decodeUnknownSync` 函数非常有用。

**示例**（使用 `decodeUnknownSync` 进行即时解码）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 模拟一个未知输入
const input: unknown = { name: "Alice", age: 30 }

// 匹配 Schema 的有效输入示例
console.log(Schema.decodeUnknownSync(Person)(input))
// 输出: { name: 'Alice', age: 30 }

// 不匹配 Schema 的无效输入示例
console.log(Schema.decodeUnknownSync(Person)(null))
/*
抛出错误:
ParseError: Expected { readonly name: string; readonly age: number }, actual null
*/
```

### decodeUnknownEither

`Schema.decodeUnknownEither` 函数允许你解析一个值，并将结果以 [Either](/docs/data-types/either/) 的形式接收，其中包含成功（`Right`）或失败（`Left`）。这种方法让你能够更优雅地处理解析错误，而无需抛出异常。

**示例**（使用 `Schema.decodeUnknownEither` 进行错误处理）

```ts twoslash
import { Schema } from "effect"
import { Either } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

const decode = Schema.decodeUnknownEither(Person)

// 模拟一个未知输入
const input: unknown = { name: "Alice", age: 30 }

// 尝试解码一个有效的输入
const result1 = decode(input)
if (Either.isRight(result1)) {
  console.log(result1.right)
  /*
  输出:
  { name: "Alice", age: 30 }
  */
}

// 模拟解码一个无效的输入
const result2 = decode(null)
if (Either.isLeft(result2)) {
  console.log(result2.left)
  /*
  输出:
  {
    _id: 'ParseError',
    message: 'Expected { readonly name: string; readonly age: number }, actual null'
  }
  */
}
```

### decodeUnknown

如果你的 Schema 涉及异步转换，那么 `Schema.decodeUnknownSync` 和 `Schema.decodeUnknownEither` 函数将不再适用。在这种情况下，你应该使用 `Schema.decodeUnknown` 函数，它会返回一个 [Effect](/docs/getting-started/the-effect-type/)。

**示例**（处理异步解码）

```ts twoslash
import { Schema } from "effect"
import { Effect } from "effect"

const PersonId = Schema.Number

const Person = Schema.Struct({
  id: PersonId,
  name: Schema.String,
  age: Schema.Number
})

const asyncSchema = Schema.transformOrFail(PersonId, Person, {
  strict: true,
  // 使用模拟的异步转换进行解码
  decode: (id) =>
    Effect.succeed({ id, name: "name", age: 18 }).pipe(
      Effect.delay("10 millis")
    ),
  encode: (person) =>
    Effect.succeed(person.id).pipe(Effect.delay("10 millis"))
})

// 尝试在异步 Schema 上使用同步解码器
console.log(Schema.decodeUnknownEither(asyncSchema)(1))
/*
输出:
{
  _id: 'Either',
  _tag: 'Left',
  left: {
    _id: 'ParseError',
    message: '(number <-> { readonly id: number; readonly name: string; readonly age: number })\n' +
      '└─ cannot be be resolved synchronously, this is caused by using runSync on an effect that performs async work'
  }
}
*/

// 使用 `Schema.decodeUnknown` 进行异步解码
Effect.runPromise(Schema.decodeUnknown(asyncSchema)(1)).then(console.log)
/*
输出:
{ id: 1, name: 'name', age: 18 }
*/
```

在上面的代码中，第一种使用 `Schema.decodeUnknownEither` 的方法会导致错误，提示转换无法同步解析。这是因为 `Schema.decodeUnknownEither` 并非为异步操作而设计。第二种方法使用了 `Schema.decodeUnknown`，它可以正常工作，允许你处理异步转换并返回预期结果。

## 编码 (Encoding)

`Schema` 模块提供了多个 `encode*` 函数，用于根据 Schema 对数据进行编码：

| API | 描述 |
| :--- | :--- |
| `encodeSync` | 同步编码数据，如果编码失败则抛出错误。 |
| `encodeOption` | 编码数据并返回 [Option](/docs/data-types/option/) 类型。 |
| `encodeEither` | 编码数据并返回一个表示成功或失败的 [Either](/docs/data-types/either/) 类型。 |
| `encodePromise` | 编码数据并返回一个 `Promise`。 |
| `encode` | 编码数据并返回一个 [Effect](/docs/getting-started/the-effect-type/)。 |

**示例**（使用 `Schema.encodeSync` 进行即时编码）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  // 确保 name 是非空字符串
  name: Schema.NonEmptyString,
  // 允许 age 从字符串解码，并编码回字符串
  age: Schema.NumberFromString
})

// 有效输入：编码成功并返回预期类型
console.log(Schema.encodeSync(Person)({ name: "Alice", age: 30 }))
// 输出: { name: 'Alice', age: '30' }

// 无效输入：由于 name 字符串为空，编码失败
console.log(Schema.encodeSync(Person)({ name: "", age: 30 }))
/*
抛出错误:
ParseError: { readonly name: NonEmptyString; readonly age: NumberFromString }
└─ ["name"]
   └─ NonEmptyString
      └─ Predicate refinement failure
         └─ Expected a non empty string, actual ""
*/
```

请注意，在编码过程中，数字值 `30` 被转换为了字符串 `"30"`。

### 处理不支持的编码

在某些情况下，支持 Schema 的编码可能并不可行。虽然通常建议定义的 Schema 应同时支持解码和编码，但在某些场景下，对特定类型进行编码是不受支持的或不必要的。在这些情况下，可以使用 `Forbidden` 错误来标记某些值无法进行编码。

**示例**（使用 `Forbidden` 表示不支持编码）

下面是一个在解码过程中永远不会失败的转换示例。它返回一个 [Either](/docs/data-types/either/)，其中包含解码后的值或原始输入。对于编码，我们可以合理地选择不支持它，并使用 `Forbidden` 作为结果。

```ts twoslash
import { Either, ParseResult, Schema } from "effect"

// 定义一个能安全解码为 Either 类型的 Schema
export const SafeDecode = <A, I>(self: Schema.Schema<A, I, never>) => {
  const decodeUnknownEither = Schema.decodeUnknownEither(self)
  return Schema.transformOrFail(
    Schema.Unknown,
    Schema.EitherFromSelf({
      left: Schema.Unknown,
      right: Schema.typeSchema(self)
    }),
    {
      strict: true,
      // 解码：将失败的结果映射为包含原始输入的 Left，
      // 将成功的结果映射为 Right
      decode: (input) =>
        ParseResult.succeed(
          Either.mapLeft(decodeUnknownEither(input), () => input)
        ),
      // 编码：仅支持编码 Right 值，
      // Left 值会引发 Forbidden 错误
      encode: (actual, _, ast) =>
        Either.match(actual, {
          onLeft: () =>
            ParseResult.fail(
              new ParseResult.Forbidden(
                ast,
                actual,
                "cannot encode a Left"
              )
            ),
          // 成功编码 Right 值
          onRight: ParseResult.succeed
        })
    }
  )
}
```

**解释**

- **解码**：`SafeDecode` 函数确保了解码永远不会失败。它将解码后的值包装在 [Either](/docs/data-types/either/) 中，其中成功的解码产生 `Right`，而失败的解码产生包含原始输入的 `Left`。
- **编码**：编码过程使用 `Forbidden` 错误来指示不支持对 `Left` 值进行编码。只有 `Right` 值才能被成功编码。

## 解析错误 (ParseError)

`Schema.decodeUnknownEither` 和 `Schema.encodeEither` 函数会返回一个 [Either](/docs/data-types/either/)：

```ts showLineNumbers=false
Either<Type, ParseError>
```

其中 `ParseError` 的定义如下（简化版）：

```ts showLineNumbers=false
interface ParseError {
  readonly _tag: "ParseError"
  readonly issue: ParseIssue
}
```

在此结构中，`ParseIssue` 表示解析过程中可能发生的错误。它被包装在一个带有标签（tagged）的错误中，以便使用 [Effect.catchTag](/docs/error-management/expected-errors/#catchtag) 更轻松地捕获错误。结果 `Either<Type, ParseError>` 包含 Schema 所描述的推断数据类型（`Type`）。解析成功时会产生一个包含解析数据 `Type` 的 `Right` 值，而解析失败则会产生一个包含 `ParseError` 的 `Left` 值。

## 解析选项 (Parse Options)

以下选项提供了对解码和编码行为的控制。

### 管理多余属性 (Managing Excess properties)

默认情况下，解析值时，Schema 中未定义的任何属性都会从输出中删除。这确保了解析后的数据严格符合预期的结构。

如果你想检测并处理非预期的属性，可以使用 `onExcessProperty` 选项（默认值为 `"ignore"`），它允许你针对多余属性抛出错误。当你需要验证并捕获未预见的属性时，这非常有用。

**示例**（将 `onExcessProperty` 设置为 `"error"`）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 默认情况下，多余属性会被忽略
console.log(
  Schema.decodeUnknownSync(Person)({
    name: "Bob",
    age: 40,
    email: "bob@example.com" // 被忽略
  })
)
/*
输出:
{ name: 'Bob', age: 40 }
*/

// 当 onExcessProperty 设置为 "error" 时，
// 遇到多余属性会抛出错误
Schema.decodeUnknownSync(Person)(
  {
    name: "Bob",
    age: 40,
    email: "bob@example.com" // 将引发错误
  },
  { onExcessProperty: "error" }
)
/*
抛出错误:
ParseError: { readonly name: string; readonly age: number }
└─ ["email"]
   └─ is unexpected, expected: "name" | "age"
*/
```

若要保留额外属性，请将 `onExcessProperty` 设置为 `"preserve"`。

**示例**（将 `onExcessProperty` 设置为 `"preserve"`）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 多余属性在输出中被保留
console.log(
  Schema.decodeUnknownSync(Person)(
    {
      name: "Bob",
      age: 40,
      email: "bob@example.com"
    },
    { onExcessProperty: "preserve" }
  )
)
/*
输出:
{ email: 'bob@example.com', name: 'Bob', age: 40 }
*/
```

### 接收所有错误 (Receive all errors)

`errors` 选项使你能够检索在解析期间遇到的所有错误。默认情况下，仅返回第一个错误。将 `errors` 设置为 `"all"` 可提供全面的错误反馈，这对于调试或提供详细的验证反馈非常有用。

**示例**（将 `errors` 设置为 `"all"`）

```ts twoslash
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 尝试解析输入数据中包含多个问题的对象
Schema.decodeUnknownSync(Person)(
  {
    name: "Bob",
    age: "abc",
    email: "bob@example.com"
  },
  { errors: "all", onExcessProperty: "error" }
)
/*
抛出错误:
ParseError: { readonly name: string; readonly age: number }
├─ ["email"]
│  └─ is unexpected, expected: "name" | "age"
└─ ["age"]
   └─ Expected number, actual "abc"
*/
```

### 管理属性顺序 (Managing Property Order)

`propertyOrder` 选项提供了对输出中对象字段顺序的控制。当键的顺序对下游处理流程很重要，或者保持输入顺序能增强可读性和易用性时，此功能特别有用。

默认情况下，`propertyOrder` 选项设置为 `"none"`。这意味着内部系统会决定键的顺序以优化解析速度。在此模式下，键的顺序不应被视为稳定的，建议不要依赖键的排序，因为它可能会在未来的更新中发生变化。

将 `propertyOrder` 设置为 `"original"` 可确保键在解码/编码过程中按照它们在输入中出现的顺序进行排序。

**示例**（同步解码）

```ts twoslash
import { Schema } from "effect"

const schema = Schema.Struct({
  a: Schema.Number,
  b: Schema.Literal("b"),
  c: Schema.Number
})

// 默认解码，属性顺序由系统定义
console.log(Schema.decodeUnknownSync(schema)({ b: "b", c: 2, a: 1 }))
// 输出可能各异: { a: 1, b: 'b', c: 2 }

// 解码并保留输入顺序
console.log(
  Schema.decodeUnknownSync(schema)(
    { b: "b", c: 2, a: 1 },
    { propertyOrder: "original" }
  )
)
// 输出保留了输入顺序: { b: 'b', c: 2, a: 1 }
```

**示例**（异步解码）

```ts twoslash
import type { Duration } from "effect"
import { Effect, ParseResult, Schema } from "effect"

// 用于模拟 Schema 中异步操作的辅助函数
const effectify = (duration: Duration.DurationInput) =>
  Schema.Number.pipe(
    Schema.transformOrFail(Schema.Number, {
      strict: true,
      decode: (x) =>
        Effect.sleep(duration).pipe(
          Effect.andThen(ParseResult.succeed(x))
        ),
      encode: ParseResult.succeed
    })
  )

// 定义一个每个字段都具有异步行为的结构
const schema = Schema.Struct({
  a: effectify("200 millis"),
  b: effectify("300 millis"),
  c: effectify("100 millis")
}).annotations({ concurrency: 3 })

// 默认解码，属性顺序由系统内部决定
Schema.decode(schema)({ a: 1, b: 2, c: 3 })
  .pipe(Effect.runPromise)
  .then(console.log)
// 内部决定的输出顺序: { c: 3, a: 1, b: 2 }

// 解码并保留输入顺序
Schema.decode(schema)({ a: 1, b: 2, c: 3 }, { propertyOrder: "original" })
  .pipe(Effect.runPromise)
  .then(console.log)
// 输出保留了输入顺序: { a: 1, b: 2, c: 3 }
```

### 在 Schema 层级自定义解析行为

`parseOptions` 注解（annotation）允许你在不同的 Schema 层级自定义解析行为，使你能够对结构中的嵌套 Schema 应用唯一的解析设置。在子 Schema 内部定义的选项会覆盖父级设置，并应用于该子 Schema 下的所有嵌套内容。

**示例**（使用 `parseOptions` 自定义错误处理）

```ts twoslash
import { Schema } from "effect"
import { Either } from "effect"

const schema = Schema.Struct({
  a: Schema.Struct({
    b: Schema.String,
    c: Schema.String
  }).annotations({
    title: "first error only",
    // 限制此子 Schema 仅显示第一个错误
    parseOptions: { errors: "first" }
  }),
  d: Schema.String
}).annotations({
  title: "all errors",
  // 捕获主 Schema 的所有错误
  parseOptions: { errors: "all" }
})

// 使用自定义错误处理行为解码输入
const result = Schema.decodeUnknownEither(schema)(
  { a: {} },
  { errors: "first" }
)
if (Either.isLeft(result)) {
  console.log(result.left.message)
}
/*
all errors
├─ ["a"]
│  └─ first error only
│     └─ ["b"]
│        └─ is missing
└─ ["d"]
   └─ is missing
*/
```

**详细输出说明：**

在此示例中：

- 主 Schema 配置为显示所有错误。因此，你会看到与 `d` 字段（因为它缺失）以及来自 `a` 子 Schema 的任何错误。
- 子 Schema (`a`) 设置为仅显示第一个错误。尽管 `b` 和 `c` 字段都缺失，但仅报告了第一个缺失的字段 (`b`)。

## 类型守卫 (Type Guards)

`Schema.is` 函数提供了一种验证值是否符合给定 Schema 的方法。它充当 [类型守卫 (type guard)](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates)，接收一个 `unknown` 类型的值，并确定其是否匹配 Schema 中定义的结构和类型约束。

以下是 `Schema.is` 函数的工作原理：

1. **Schema 定义**：定义一个 Schema 来描述你期望的数据结构的类型和约束。例如，`Schema<Type, Encoded, Context>`，其中 `Type` 是你想要验证的目标类型。

2. **类型守卫创建**：使用该 Schema 创建一个用户定义的类型守卫：`(u: unknown) => u is Type`。此函数可在运行时用于检查值是否满足 Schema 的要求。

---
**Encoded 类型在类型守卫中的作用**
> 在 Schema 转换中经常使用的 `Encoded` 类型不会影响类型守卫的创建。其主要目的是确保输入匹配所需的目标类型 `Type`。
---

**示例**（创建并使用类型守卫）

```ts twoslash
import { Schema } from "effect"

// 为 Person 对象定义一个 Schema
const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 从 Schema 生成一个类型守卫
const isPerson = Schema.is(Person)

// 使用各种输入测试类型守卫
console.log(isPerson({ name: "Alice", age: 30 }))
// 输出: true

console.log(isPerson(null))
// 输出: false

console.log(isPerson({}))
// 输出: false
```

生成的 `isPerson` 函数具有以下签名：

```ts showLineNumbers=false
const isPerson: (
  u: unknown,
  overrideOptions?: number | ParseOptions
) => u is {
  readonly name: string
  readonly age: number
}
```
# 断言 (Assertions)

虽然类型守卫用于验证一个值是否符合特定类型，但 `Schema.asserts` 函数更进一步，它会断言输入是否匹配 Schema 类型 `Type`（来自 `Schema<Type, Encoded, Context>`）。如果输入不匹配 Schema，它会抛出一个详细的错误，这使得它在运行时验证中非常有用。

<Aside type="note" title="Encoded 类型在断言中的作用">
  在 Schema 转换中经常使用的 `Encoded` 类型不会影响断言的创建。其主要目的是确保输入匹配所需的目标类型 `Type`。
</Aside>

**示例**（创建并使用断言）

```ts twoslash
import { Schema } from "effect"

// 为 Person 对象定义一个 Schema
const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 从 Schema 生成一个断言函数
const assertsPerson: Schema.Schema.ToAsserts<typeof Person> =
  Schema.asserts(Person)

try {
  // 尝试断言输入匹配 Person Schema
  assertsPerson({ name: "Alice", age: "30" })
} catch (e) {
  console.error("输入不匹配 Schema：")
  console.error(e)
}
/*
抛出错误:
输入不匹配 Schema：
{
  _id: 'ParseError',
  message: '{ readonly name: string; readonly age: number }\n' +
    '└─ ["age"]\n' +
    '   └─ Expected number, actual "30"'
}
*/

// 此输入匹配 Schema，不会抛出错误
assertsPerson({ name: "Alice", age: 30 })
```

从该 Schema 生成的 `assertsPerson` 函数具有以下签名：

```ts showLineNumbers=false
const assertsPerson: (
  input: unknown,
  overrideOptions?: number | ParseOptions
) => asserts input is {
  readonly name: string
  readonly age: number
}
```

## 管理缺失属性 (Managing Missing Properties)

在解码时，了解如何处理缺失属性至关重要。默认情况下，如果输入中不存在某个属性，它会被视为该属性存在且值为 `undefined`。

**示例**（缺失属性的默认行为）

```ts twoslash
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.decodeUnknownSync(schema)(input))
// 输出: { a: undefined }
```

在这个例子中，尽管键 `"a"` 在输入中并不存在，但默认情况下它被处理为 `{ a: undefined }`。

如果你需要验证逻辑能够区分“真正缺失的属性”和“显式设置为 `undefined` 的属性”，你可以启用 `exact` 选项。

**示例**（设置 `exact: true` 以区分缺失属性）

```ts twoslash
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.decodeUnknownSync(schema)(input, { exact: true }))
/*
抛出错误
ParseError: { readonly a: unknown }
└─ ["a"]
   └─ is missing
*/
```

然而，对于 `Schema.is` 和 `Schema.asserts` API，默认行为是严格处理缺失属性，即 `exact` 的默认值为 `true`：

**示例**（`Schema.is` 和 `Schema.asserts` 对缺失属性的严格处理）

```ts twoslash
import type { SchemaAST } from "effect"
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.is(schema)(input))
// 输出: false

console.log(Schema.is(schema)(input, { exact: false }))
// 输出: true

const asserts: (
  u: unknown,
  overrideOptions?: SchemaAST.ParseOptions
) => asserts u is {
  readonly a: unknown
} = Schema.asserts(schema)

try {
  asserts(input)
  console.log("asserts passed")
} catch (e: any) {
  console.error("asserts failed")
  console.error(e.message)
}
/*
输出:
asserts failed
{ readonly a: unknown }
└─ ["a"]
  └─ is missing
*/

try {
  asserts(input, { exact: false })
  console.log("asserts passed")
} catch (e: any) {
  console.error("asserts failed")
  console.error(e.message)
}
// 输出: asserts passed
```

## 命名约定 (Naming Conventions)

`effect/Schema` 中的命名约定旨在直观且合乎逻辑，**主要侧重于与 JSON 序列化的兼容性**。这种方法简化了对 Schema 的理解和使用，特别是对于那些正在集成 Web 技术（JSON 是标准的交换格式）的开发者。

### 命名策略概览

**JSON 兼容类型**

对于自然序列化为 JSON 兼容格式的 Schema，直接以其数据类型命名。

例如：

- `Schema.Date`：将 JavaScript `Date` 对象序列化为 ISO 格式的字符串，这是 JSON 中表示日期的典型方法。
- `Schema.Number`：直接使用，因为它精确映射到 JSON 的数字类型，无需特殊转换即可保持 JSON 兼容。

**非 JSON 兼容类型**

在处理没有直接 JSON 表示的类型时，命名策略会包含额外的细节来指示必要的转换。这有助于对 Schema 的行为建立明确的预期：

例如：

- `Schema.DateFromSelf`：表示该 Schema 处理的是 `Date` 对象（原生对象），这些对象本身并不是原生 JSON 可序列化的。
- `Schema.NumberFromString`：此命名暗示该 Schema 处理最初表示为字符串的数字，强调了解码时从字符串到数字的转换。

这些 Schema 的主要目标是确保领域对象可以轻松地进行序列化（“编码”）和反序列化（“解码”），以便通过网络连接进行传输，从而促进应用程序不同部分之间或不同应用程序之间的数据转移。

### 核心理念 (Rationale)

虽然 JSON 的普遍性使其成为命名的首要考量，但这些约定也兼顾了其他传输类型的序列化。例如，将 `Date` 转换为字符串是各种通信协议（不仅仅是 JSON）通用的有用方法。因此，所选的命名约定作为合理的默认设置，优先考虑了清晰性和易用性，促进了跨多种技术环境的序列化和反序列化过程。`
