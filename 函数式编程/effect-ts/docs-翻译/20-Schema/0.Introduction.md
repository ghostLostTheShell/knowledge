欢迎阅读 `effect/Schema` 文档，这是一个用于在 TypeScript 中定义模式、验证和转换数据的模块。

`effect/Schema` 模块允许你定义一个 `Schema<Type, Encoded, Requirements>`，它为描述数据结构和数据类型提供蓝图。一旦定义完成，你可以利用该模式执行一系列操作，包括：

| 操作 | 描述 |
| --------------- | ------------------------------------------------------------------------------------ |
| 解码 (Decoding) | 将数据从输入类型 `Encoded` 转换为输出类型 `Type`。 |
| 编码 (Encoding) | 将数据从输出类型 `Type` 转换回输入类型 `Encoded`。 |
| 断言 (Asserting) | 验证一个值是否符合模式的输出类型 `Type`。 |
| 标准模式 (Standard Schema) | 生成 [Standard Schema V1](https://standardschema.dev/)。 |
| 任意值 (Arbitraries) | 为 [fast-check](https://github.com/dubzzz/fast-check) 测试生成任意值。 |
| JSON 模式 (JSON Schemas) | 根据定义的模式创建 JSON Schema。 |
| 等价性 (Equivalence) | 根据定义的模式创建 [等价性检查 (Equivalence)](/docs/schema/equivalence/)。 |
| 美化打印 (Pretty printing) | 支持对数据结构进行美化打印。 |

## 环境要求

- TypeScript 5.4 或更高版本。
- 在 `tsconfig.json` 文件中启用 `strict` 标志。
- （可选）在 `tsconfig.json` 文件中启用 `exactOptionalPropertyTypes` 标志。

```json showLineNumbers=false
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true // 可选
  }
}
```

### exactOptionalPropertyTypes 选项

`effect/Schema` 模块利用了 `tsconfig.json` 中的 `exactOptionalPropertyTypes` 选项。此选项会影响可选属性的类型定义（要了解更多关于此选项的信息，可以参考 [TypeScript 官方文档](https://www.typescriptlang.org/tsconfig#exactOptionalPropertyTypes)）。

**示例**（启用 `exactOptionalPropertyTypes`）
```ts
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.optionalWith(Schema.NonEmptyString, { exact: true })
})

type Type = Schema.Schema.Type<typeof Person>
/*
type Type = {
    readonly name?: string;
}
*/

// @errors: 2379
Schema.decodeSync(Person)({ name: undefined })
```

在这里，请注意 `name` 的类型是“精确的”（`string`），这意味着类型检查器会捕获任何尝试分配无效值（如 `undefined`）的行为。

**示例**（禁用 `exactOptionalPropertyTypes`）

如果由于某种原因（可能与第三方库冲突）你无法启用 `exactOptionalPropertyTypes` 选项，你仍然可以使用 `effect/Schema`。但是，类型与运行时行为之间会出现不匹配：

```ts
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.optionalWith(Schema.NonEmptyString, { exact: true })
})

type Type = Schema.Schema.Type<typeof Person>
/*
type Type = {
    readonly name?: string | undefined;
}
*/

// No type error, but a decoding failure occurs
Schema.decodeSync(Person)({ name: undefined })
/*
throws:
ParseError: { readonly name?: NonEmptyString }
└─ ["name"]
   └─ NonEmptyString
      └─ From side refinement failure
         └─ Expected string, actual undefined
*/
```



在这种情况下，`name` 的类型被放宽为 `string | undefined`，这意味着类型检查器不会捕获无效值（`undefined`）。然而，在解码过程中，你会遇到错误，提示不允许使用 `undefined`。

## Schema 类型

模式（Schema）是一个描述数据结构的不可变值，由 `Schema` 类型表示。

以下是 `Schema` 的一般形式：

```text showLineNumbers=false
         ┌─── 解码后的值类型
         │        ┌─── 编码后的类型（输入/输出）
         │        │      ┌─── 环境要求（上下文）
         ▼        ▼      ▼
Schema<Type, Encoded, Requirements>
```

`Schema` 类型具有三个具有以下含义的类型参数：

| 参数 | 描述 |
| --- | --- |
| **Type** | 表示模式在解码成功时产生的值类型。 |
| **Encoded** | 表示模式在编码成功时产生的值类型。默认情况下，如果不显式提供，它等于 `Type`。 |
| **Requirements** | 类似于 [`Effect`](https://effect.website/docs/getting-started/the-effect-type) 类型，它表示模式在执行解码和编码时所需的上下文数据。如果此类型参数为 `never`（默认值），则表示该模式没有依赖要求。 |

**示例**

- `Schema<string>`（默认为 `Schema<string, string, never>`）表示一个解码为 `string`、编码为 `string` 且没有环境要求的模式。
- `Schema<number, string>`（默认为 `Schema<number, string, never>`）表示一个从 `string` 解码为 `number`、将 `number` 编码为 `string` 且没有环境要求的模式。

> **类型参数缩写注记**：在 Effect 生态系统中，你经常会看到 `Schema` 的类型参数分别缩写为 `A`、`I` 和 `R`。这只是类型值 **A**、输入 (**I**nput) 和环境要求 (**R**equirements) 的简写。

## 理解 Schema 值

**不可变性**。`Schema` 值是不可变的，`effect/Schema` 模块中的每个函数都会产生一个新的 `Schema` 值。

**建模数据结构**。这些值本身不执行任何操作，它们只是建模或描述数据的结构。

**由编译器解释**。一个 `Schema` 可以被各种“编译器”解释为特定的操作，具体取决于编译器类型（解码、编码、美化打印、任意值等）。

## 理解解码（Decoding）与编码（Encoding）

在 TypeScript 中处理数据时，你经常需要处理来自或发送到外部系统的数据。这些数据可能并不总是符合你预期的格式或类型，尤其是在处理用户输入、API 数据或以不同格式存储的数据时。为了处理这些差异，我们使用**解码**和**编码**。

| 术语 | 描述 |
| --- | --- |
| **解码 (Decoding)** | 用于从你无法控制数据格式的外部来源解析数据。 |
| **编码 (Encoding)** | 用于向外部来源发送数据，将其转换为这些来源期望的格式。 |

例如，在前端处理表单时，你经常会收到字符串形式的无类型数据。这些数据可能会被篡改，且原生不支持数组或布尔值。解码帮助你验证并将这些数据解析为更有用的类型，如数字、日期和数组。编码则允许你将这些类型转换回表单期望的字符串格式。

下面的图表展示了使用 `Schema<A, I, R>` 进行编码和解码之间的关系：

```txt

| unknown |       | A |       | I |       | unknown |
└─────────┘       └───┘       └───┘       └─────────┘
     |              |           |              |
     | validate     |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | is           |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | asserts      |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | encodeUnknown|           |              |
     |─────────────────────────►|              |
                    |           |              |

                    |──────────►│              |
                    |           |              |

                    |           |              |
```

我们将使用 `Schema<Date, string, never>` 的例子来拆解这些概念。该模式作为一个工具，将 `string` 转换为 `Date`，反之亦然。

### 编码 (Encoding)

当我们谈论“编码”时，我们指的是将 `Date` 更改为 `string` 的过程。简单来说，这就是将数据从一种格式转换为另一种格式的行为。

### 解码 (Decoding)

相反，“解码”意味着将 `string` 还原为 `Date`。它本质上是编码的反向操作，将数据恢复为其原始形式。

### 从未知类型解码 (Decoding From Unknown)

从 `unknown` 解码涉及两个关键步骤：

1. **检查**：首先，我们验证输入数据（其类型为 `unknown`）是否符合预期结构。在我们的特定案例中，这意味着确保输入确实是一个 `string`。
2. **解码**：检查成功后，我们继续将 `string` 转换为 `Date`。这个过程完成了解码操作，其中数据既经过了验证又完成了转换。

### 从未知类型编码 (Encoding From Unknown)

从 `unknown` 编码涉及两个关键步骤：

1. **检查**：首先，我们验证输入数据（其类型为 `unknown`）是否符合预期结构。在我们的特定案例中，这意味着确保输入确实是一个 `Date`。
2. **编码**：检查成功后，我们继续将 `Date` 转换为 `string`。这个过程完成了编码操作，其中数据既经过了验证又完成了转换。

## 模式准则 (The Rule of Schemas)

在使用模式时，有一个重要的准则需要记住：你的模式应当以这样一种方式构建——当你同时执行编码和解码操作时，最终应当得到原始值。

简单来说，如果你对一个值进行编码并立即对其解码，结果应当与你起始的原始值一致。这条准则确保了你的数据在整个编码和解码过程中保持一致性和可靠性。

> **提示：确保一致性**。作为一般准则，模式定义应保证：编码 + 解码能够返回原始值。
