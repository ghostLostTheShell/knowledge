**快速入门**

你可以从 `effect/Schema` 模块导入必要的类型和函数：

**示例（命名空间导入）**

```typescript
import * as Schema from "effect/Schema"
```

**示例（命名导入）**

```typescript
import { Schema } from "effect"
```

### 定义模式

定义模式的一种常见方法是使用 `Struct` 构造函数。这个构造函数允许你创建一个新的模式，该模式描述了一个具有特定属性的对象。对象中的每个属性都由其自己的模式定义，该模式指定了数据类型和任何验证规则。

**示例（定义一个简单的对象模式）**

这个 `Person` 模式描述了一个具有 `name`（字符串）和 `age`（数字）属性的对象：

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})
```

### 提取推断类型

#### Type

一旦你定义了一个模式（`Schema<Type, Encoded, Context>`），你可以通过两种方式提取推断的类型 `Type`：

1.  使用 `Schema.Type` 工具类型
2.  直接访问模式上的 `Type` 字段

**示例（提取推断类型）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 1. 使用 Schema.Type 工具类型
type Person = Schema.Schema.Type<typeof Person>

// 2. 直接访问 Type 字段
type Person2 = typeof Person.Type
```

生成的类型如下所示：

```typescript
type Person = {
  readonly name: string
  readonly age: number
}
```

或者，你可以使用 `interface` 关键字提取 `Person` 类型，这在某些情况下可以提高可读性和性能。

**示例（使用接口提取类型）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

interface Person extends Schema.Schema.Type<typeof Person> {}
```

两种方法产生相同的结果，但使用 `interface` 具有性能优势和可读性提升等好处。

#### Encoded

在 `Schema<Type, Encoded, Context>` 中，`Encoded` 类型可能与 `Type` 类型不同，它表示数据编码的格式。你可以通过两种方式提取 `Encoded` 类型：

1.  使用 `Schema.Encoded` 工具类型
2.  直接访问模式上的 `Encoded` 字段

**示例（提取 Encoded 类型）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  // 一个将字符串解码为数字的模式
  age: Schema.NumberFromString
})

// 1. 使用 Schema.Encoded 工具类型
type PersonEncoded = Schema.Schema.Encoded<typeof Person>

// 2. 直接访问 Encoded 字段
type PersonEncoded2 = typeof Person.Encoded
```

生成的类型是：

```typescript
type PersonEncoded = {
  readonly name: string
  readonly age: string
}
```

注意，在模式的 `Encoded` 类型中，`age` 是 `string` 类型，而在模式的 `Type` 类型中，`age` 是 `number` 类型。

或者，你可以使用 `interface` 关键字定义 `PersonEncoded` 类型，这可以增强可读性和性能。

**示例（使用接口提取 Encoded 类型）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  // 一个将字符串解码为数字的模式
  age: Schema.NumberFromString
})

interface PersonEncoded extends Schema.Schema.Encoded<typeof Person> {}
```

两种方法产生相同的结果，但使用 `interface` 具有性能优势和可读性提升等好处。

#### Context

在 `Schema<Type, Encoded, Context>` 中，`Context` 类型表示模式执行编码或解码所需的任何外部数据或依赖项。你可以通过两种方式提取推断的 `Context` 类型：

1.  使用 `Schema.Context` 工具类型。
2.  访问模式上的 `Context` 字段。

**示例（提取 Context 类型）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 1. 使用 Schema.Context 工具类型
type PersonContext = Schema.Schema.Context<typeof Person>

// 2. 直接访问 Context 字段
type PersonContext2 = typeof Person.Context
```

### 具有不透明类型的模式

定义模式时，你可能希望创建一个具有不透明类型的模式。当你想要隐藏模式的内部结构，只暴露模式的类型时，这很有用。

**示例（创建不透明模式）**

要创建一个具有不透明类型的模式，你可以使用以下重新声明模式的技术：

```typescript
import { Schema } from "effect"

// 定义模式结构
const _Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 声明类型接口以使其不透明
interface Person extends Schema.Schema.Type<typeof _Person> {}

// 将模式重新声明为不透明
const Person: Schema.Schema<Person> = _Person
```

或者，你可以使用 Class API（有关更多详细信息，请参阅 Class API 部分）。

请注意，当模式的定义使得 `Type` 与 `Encoded` 不同时，上述技术会变得更复杂。

**示例（Type 和 Encoded 不同的不透明模式）**

```typescript
import { Schema } from "effect"

// 定义模式结构，其中一个字段将字符串解码为数字
const _Person = Schema.Struct({
  name: Schema.String,
  age: Schema.NumberFromString
})

// 为不透明模式创建 `Type` 接口
interface Person extends Schema.Schema.Type<typeof _Person> {}

// 为不透明模式创建 `Encoded` 接口
interface PersonEncoded extends Schema.Schema.Encoded<typeof _Person> {}

// 使用不透明的 Type 和 Encoded 重新声明模式
const Person: Schema.Schema<Person, PersonEncoded> = _Person
```

在这种情况下，字段 `"age"` 在模式的 `Encoded` 类型中是 `string` 类型，在模式的 `Type` 类型中是 `number` 类型。因此，我们需要定义两个接口（`PersonEncoded` 和 `Person`），并使用它们来重新声明最终的模式 `Person`。

### 默认只读类型

需要注意的是，默认情况下，`effect/Schema` 导出的大多数构造函数返回只读类型。

**示例（模式中的只读类型）**

例如，在下面的 `Person` 模式中：

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})
```

推断出的类型将是：

```typescript

```

### 解码

在 TypeScript 中处理未知数据类型时，将它们解码为已知结构可能具有挑战性。幸运的是，`effect/Schema` 提供了几个函数来帮助完成这个过程。让我们探索如何使用这些函数解码未知值。

| API | 描述 |
| :--- | :--- |
| `decodeUnknownSync` | 同步解码一个值，如果解析失败则抛出错误。 |
| `decodeUnknownOption` | 解码一个值并返回一个 `Option` 类型。 |
| `decodeUnknownEither` | 解码一个值并返回一个 `Either` 类型。 |
| `decodeUnknownPromise` | 解码一个值并返回一个 `Promise`。 |
| `decodeUnknown` | 解码一个值并返回一个 `Effect`。 |

#### `decodeUnknownSync`

当你想要解析一个值并在解析失败时立即抛出错误时，`Schema.decodeUnknownSync` 函数非常有用。

**示例（使用 decodeUnknownSync 进行即时解码）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 模拟一个未知输入
const input: unknown = { name: "Alice", age: 30 }

// 有效输入匹配模式的示例
console.log(Schema.decodeUnknownSync(Person)(input))
// 输出: { name: 'Alice', age: 30 }

// 无效输入不匹配模式的示例
console.log(Schema.decodeUnknownSync(Person)(null))
/*
抛出:
ParseError: Expected { readonly name: string; readonly age: number }, actual null
*/
```

#### `decodeUnknownEither`

`Schema.decodeUnknownEither` 函数允许你解析一个值并将结果作为 `Either` 接收，表示成功（`Right`）或失败（`Left`）。这种方法让你可以更优雅地处理解析错误，而无需抛出异常。

**示例（使用 Schema.decodeUnknownEither 进行错误处理）**

```typescript
import { Schema } from "effect"
import { Either } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

const decode = Schema.decodeUnknownEither(Person)

// 模拟一个未知输入
const input: unknown = { name: "Alice", age: 30 }

// 尝试解码有效输入
const result1 = decode(input)
if (Either.isRight(result1)) {
  console.log(result1.right)
  /*
  输出:
  { name: "Alice", age: 30 }
  */
}

// 模拟解码无效输入
const result2 = decode(null)
if (Either.isLeft(result2)) {
  console.log(result2.left)
  /*
  输出:
  {
    _id: 'ParseError',
    message: 'Expected { readonly name: string; readonly age: number }, actual null'
  }
  */
}
```

#### `decodeUnknown`

如果你的模式涉及异步转换，`Schema.decodeUnknownSync` 和 `Schema.decodeUnknownEither` 函数将不适用。在这种情况下，你应该使用 `Schema.decodeUnknown` 函数，它返回一个 `Effect`。

**示例（处理异步解码）**

```typescript
import { Schema } from "effect"
import { Effect } from "effect"

const PersonId = Schema.Number

const Person = Schema.Struct({
  id: PersonId,
  name: Schema.String,
  age: Schema.Number
})

const asyncSchema = Schema.transformOrFail(PersonId, Person, {
  strict: true,
  // 使用模拟的异步转换进行解码
  decode: (id) =>
    Effect.succeed({ id, name: "name", age: 18 }).pipe(
      Effect.delay("10 millis")
    ),
  encode: (person) =>
    Effect.succeed(person.id).pipe(Effect.delay("10 millis"))
})

// 尝试在异步模式上使用同步解码器
console.log(Schema.decodeUnknownEither(asyncSchema)(1))
/*
输出:
{
  _id: 'Either',
  _tag: 'Left',
  left: {
    _id: 'ParseError',
    message: '(number <-> { readonly id: number; readonly name: string; readonly age: number })\n' +
      '└─ cannot be be resolved synchronously, this is caused by using runSync on an effect that performs async work'
  }
}
*/

// 使用 `Schema.decodeUnknown` 进行异步解码
Effect.runPromise(Schema.decodeUnknown(asyncSchema)(1)).then(console.log)
/*
输出:
{ id: 1, name: 'name', age: 18 }
*/
```

在上面的代码中，第一种使用 `Schema.decodeUnknownEither` 的方法导致一个错误，表明转换无法同步解析。这是因为 `Schema.decodeUnknownEither` 不是为异步操作设计的。第二种使用 `Schema.decodeUnknown` 的方法正常工作，允许你处理异步转换并返回预期结果。

### 编码

`Schema` 模块提供了几个 `encode*` 函数来根据模式编码数据：

| API | 描述 |
| :--- | :--- |
| `encodeSync` | 同步编码数据，如果编码失败则抛出错误。 |
| `encodeOption` | 编码数据并返回一个 `Option` 类型。 |
| `encodeEither` | 编码数据并返回表示成功或失败的 `Either` 类型。 |
| `encodePromise` | 编码数据并返回一个 `Promise`。 |
| `encode` | 编码数据并返回一个 `Effect`。 |

**示例（使用 Schema.encodeSync 进行即时编码）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  // 确保 name 是非空字符串
  name: Schema.NonEmptyString,
  // 允许 age 从字符串解码并编码为字符串
  age: Schema.NumberFromString
})

// 有效输入：编码成功并返回预期类型
console.log(Schema.encodeSync(Person)({ name: "Alice", age: 30 }))
// 输出: { name: 'Alice', age: '30' }

// 无效输入：由于 name 是空字符串，编码失败
console.log(Schema.encodeSync(Person)({ name: "", age: 30 }))
/*
抛出:
ParseError: { readonly name: NonEmptyString; readonly age: NumberFromString }
└─ ["name"]
   └─ NonEmptyString
      └─ Predicate refinement failure
         └─ Expected a non empty string, actual ""
*/
```

注意，在编码过程中，数字值 `30` 被转换为字符串 `"30"`。

### 处理不支持的编码

在某些情况下，支持模式的编码可能不可行。虽然通常建议定义同时允许解码和编码的模式，但有时对特定类型进行编码要么不支持，要么不必要。在这些情况下，`Forbidden` 问题可以表明对某些值进行编码不可用。

**示例（使用 Forbidden 指示不支持的编码）**

这里是一个转换的示例，它在解码过程中永远不会失败。它返回一个 `Either`，其中包含解码后的值或原始输入。对于编码，不支持它是合理的，并使用 `Forbidden` 作为结果。

```typescript
import { Either, ParseResult, Schema } from "effect"

// 定义一个安全解码为 Either 类型的模式
export const SafeDecode = <A, I>(self: Schema.Schema<A, I, never>) => {
  const decodeUnknownEither = Schema.decodeUnknownEither(self)
  return Schema.transformOrFail(
    Schema.Unknown,
    Schema.EitherFromSelf({
      left: Schema.Unknown,
      right: Schema.typeSchema(self)
    }),
    {
      strict: true,
      // 解码：将失败的结果映射为 Left（包含输入），
      // 成功的结果映射为 Right
      decode: (input) =>
        ParseResult.succeed(
          Either.mapLeft(decodeUnknownEither(input), () => input)
        ),
      // 编码：仅支持编码 Right 值，
      // Left 值引发 Forbidden 错误
      encode: (actual, _, ast) =>
        Either.match(actual, {
          onLeft: () =>
            ParseResult.fail(
              new ParseResult.Forbidden(
                ast,
                actual,
                "cannot encode a Left"
              )
            ),
          // 成功编码 Right 值
          onRight: ParseResult.succeed
        })
    }
  )
}
```

**解释**

*   **解码**：`SafeDecode` 函数确保解码永远不会失败。它将解码后的值包装在 `Either` 中，其中成功的解码产生 `Right`，失败的解码产生包含原始输入的 `Left`。
*   **编码**：编码过程使用 `Forbidden` 错误来表示不支持编码 `Left` 值。只有 `Right` 值被成功编码。

### ParseError

`Schema.decodeUnknownEither` 和 `Schema.encodeEither` 函数返回一个 `Either`：

```typescript
Either<Type, ParseError>
```

其中 `ParseError` 定义如下（简化版）：

```typescript
interface ParseError {
  readonly _tag: "ParseError"
  readonly issue: ParseIssue
}
```

在这个结构中，`ParseIssue` 表示解析过程中可能发生的错误。它被包装在一个带标签的错误中，以便更容易使用 `Effect.catchTag` 捕获错误。结果 `Either<Type, ParseError>` 包含模式描述的推断数据类型（`Type`）。成功解析会产生一个包含已解析数据 `Type` 的 `Right` 值，而解析失败则会产生一个包含 `ParseError` 的 `Left` 值。

### 解析选项

以下选项提供对解码和编码行为的控制。

#### 管理多余属性

默认情况下，在解析一个值时，模式中未定义的任何属性都会从输出中删除。这确保了解析后的数据严格符合预期的结构。

如果你想检测并处理意外属性，可以使用 `onExcessProperty` 选项（默认值：`"ignore"`），它允许你为多余属性引发错误。当你需要验证并捕获意外属性时，这很有帮助。

**示例（将 onExcessProperty 设置为 "error"）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 默认情况下，多余属性被忽略
console.log(
  Schema.decodeUnknownSync(Person)({
    name: "Bob",
    age: 40,
    email: "bob@example.com" // 被忽略
  })
)
/*
输出:
{ name: 'Bob', age: 40 }
*/

// 将 `onExcessProperty` 设置为 "error" 时，
// 多余属性会抛出错误
Schema.decodeUnknownSync(Person)(
  {
    name: "Bob",
    age: 40,
    email: "bob@example.com" // 将引发错误
  },
  { onExcessProperty: "error" }
)
/*
抛出
ParseError: { readonly name: string; readonly age: number }
└─ ["email"]
   └─ is unexpected, expected: "name" | "age"
*/
```

要保留额外属性，请将 `onExcessProperty` 设置为 `"preserve"`。

**示例（将 onExcessProperty 设置为 "preserve"）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 输出中保留多余属性
console.log(
  Schema.decodeUnknownSync(Person)(
    {
      name: "Bob",
      age: 40,
      email: "bob@example.com"
    },
    { onExcessProperty: "preserve" }
  )
)
/*
{ email: 'bob@example.com', name: 'Bob', age: 40 }
*/
```

#### 接收所有错误

`errors` 选项使你能够检索解析过程中遇到的所有错误。默认情况下，只返回第一个错误。将 `errors` 设置为 `"all"` 可以提供全面的错误反馈，这对于调试或提供详细的验证反馈很有用。

**示例（将 errors 设置为 "all"）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 尝试解析输入数据中存在多个问题的数据
Schema.decodeUnknownSync(Person)(
  {
    name: "Bob",
    age: "abc",
    email: "bob@example.com"
  },
  { errors: "all", onExcessProperty: "error" }
)
/*
抛出
ParseError: { readonly name: string; readonly age: number }
├─ ["email"]
│  └─ is unexpected, expected: "name" | "age"
└─ ["age"]
   └─ Expected number, actual "abc"
*/
```

#### 管理属性顺序

`propertyOrder` 选项提供了对输出中对象字段顺序的控制。当键的顺序对消费过程很重要，或者保持输入顺序以增强可读性和可用性时，此功能特别有用。

默认情况下，`propertyOrder` 选项设置为 `"none"`。这意味着内部系统决定键的顺序以优化解析速度。在这种模式下，键的顺序不应被认为是稳定的，建议不要依赖键的顺序，因为它可能在未来的更新中发生变化。

将 `propertyOrder` 设置为 `"original"` 可以确保在解码/编码过程中，键按照它们在输入中出现的顺序排列。

**示例（同步解码）**

```typescript
import { Schema } from "effect"

const schema = Schema.Struct({
  a: Schema.Number,
  b: Schema.Literal("b"),
  c: Schema.Number
})

// 默认解码，属性顺序由系统定义
console.log(Schema.decodeUnknownSync(schema)({ b: "b", c: 2, a: 1 }))
// 输出可能不同: { a: 1, b: 'b', c: 2 }

// 解码时保留输入顺序
console.log(
  Schema.decodeUnknownSync(schema)(
    { b: "b", c: 2, a: 1 },
    { propertyOrder: "original" }
  )
)
// 输出保留输入顺序: { b: 'b', c: 2, a: 1 }
```

**示例（异步解码）**

```typescript
import type { Duration } from "effect"
import { Effect, ParseResult, Schema } from "effect"

// 辅助函数，在模式中模拟异步操作
const effectify = (duration: Duration.DurationInput) =>
  Schema.Number.pipe(
    Schema.transformOrFail(Schema.Number, {
      strict: true,
      decode: (x) =>
        Effect.sleep(duration).pipe(
          Effect.andThen(ParseResult.succeed(x))
        ),
      encode: ParseResult.succeed
    })
  )

// 定义一个结构，每个字段都有异步行为
const schema = Schema.Struct({
  a: effectify("200 millis"),
  b: effectify("300 millis"),
  c: effectify("100 millis")
}).annotations({ concurrency: 3 })

// 默认解码，属性顺序由系统定义
Schema.decode(schema)({ a: 1, b: 2, c: 3 })
  .pipe(Effect.runPromise)
  .then(console.log)
// 输出由内部决定: { c: 3, a: 1, b: 2 }

// 解码时保留输入顺序
Schema.decode(schema)({ a: 1, b: 2, c: 3 }, { propertyOrder: "original" })
  .pipe(Effect.runPromise)
  .then(console.log)
// 输出保留输入顺序: { a: 1, b: 2, c: 3 }
```

#### 在模式级别自定义解析行为

`parseOptions` 注解允许你在不同的模式级别自定义解析行为，使你能够将独特的解析设置应用于结构中的嵌套模式。模式中定义的选项会覆盖父级设置，并应用于所有嵌套模式。

**示例（使用 parseOptions 自定义错误处理）**

```typescript
import { Schema } from "effect"
import { Either } from "effect"

const schema = Schema.Struct({
  a: Schema.Struct({
    b: Schema.String,
    c: Schema.String
  }).annotations({
    title: "first error only",
    // 在此子模式中将错误限制为第一个
    parseOptions: { errors: "first" }
  }),
  d: Schema.String
}).annotations({
  title: "all errors",
  // 为主模式捕获所有错误
  parseOptions: { errors: "all" }
})

// 使用自定义错误处理行为解码输入
const result = Schema.decodeUnknownEither(schema)(
  { a: {} },
  { errors: "first" }
)
if (Either.isLeft(result)) {
  console.log(result.left.message)
}
/*
all errors
├─ ["a"]
│  └─ first error only
│     └─ ["b"]
│        └─ is missing
└─ ["d"]
   └─ is missing
*/
```

**详细输出解释：**

在这个例子中：

*   主模式配置为显示所有错误。因此，你将看到与 `d` 字段（因为它是缺失的）相关的错误以及来自 `a` 子模式的任何错误。
*   子模式（`a`）设置为仅显示第一个错误。尽管 `b` 和 `c` 字段都缺失，但只报告第一个缺失的字段（`b`）。

### 类型守卫

`Schema.is` 函数提供了一种验证值是否符合给定模式的方法。它充当类型守卫，接受一个类型为 `unknown` 的值，并确定它是否匹配模式中定义的结构和类型约束。

`Schema.is` 函数的工作原理如下：

*   **模式定义**：定义一个模式来描述你期望的数据类型的结构和约束。例如，`Schema<Type, Encoded, Context>`，其中 `Type` 是你要验证的目标类型。
*   **类型守卫创建**：使用模式创建一个用户定义的类型守卫 `(u: unknown) => u is Type`。这个函数可以在运行时用于检查一个值是否满足模式的要求。

**Encoded 类型在类型守卫中的作用**

`Encoded` 类型（通常在模式转换中使用）不影响类型守卫的创建。主要目的是确保输入匹配期望的类型 `Type`。

**示例（创建和使用类型守卫）**

```typescript
import { Schema } from "effect"

// 为 Person 对象定义一个模式
const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 从模式生成一个类型守卫
const isPerson = Schema.is(Person)

// 使用各种输入测试类型守卫
console.log(isPerson({ name: "Alice", age: 30 }))
// 输出: true

console.log(isPerson(null))
// 输出: false

console.log(isPerson({}))
// 输出: false
```

生成的 `isPerson` 函数具有以下签名：

```typescript
const isPerson: (
  u: unknown,
  overrideOptions?: number | ParseOptions
) => u is {
  readonly name: string
  readonly age: number
}
```

### 断言

虽然类型守卫验证一个值是否符合特定类型，但 `Schema.asserts` 函数更进一步，断言输入匹配模式类型 `Type`（来自 `Schema<Type, Encoded, Context>`）。如果输入不匹配模式，它会抛出一个详细的错误，使其在运行时验证中很有用。

**Encoded 类型在断言中的作用**

`Encoded` 类型（通常在模式转换中使用）不影响断言的创建。主要目的是确保输入匹配期望的类型 `Type`。

**示例（创建和使用断言）**

```typescript
import { Schema } from "effect"

// 为 Person 对象定义一个模式
const Person = Schema.Struct({
  name: Schema.String,
  age: Schema.Number
})

// 从模式生成一个断言函数
const assertsPerson: Schema.Schema.ToAsserts<typeof Person> =
  Schema.asserts(Person)

try {
  // 尝试断言输入匹配 Person 模式
  assertsPerson({ name: "Alice", age: "30" })
} catch (e) {
  console.error("输入不匹配模式:")
  console.error(e)
}
/*
抛出:
输入不匹配模式:
{
  _id: 'ParseError',
  message: '{ readonly name: string; readonly age: number }\n' +
    '└─ ["age"]\n' +
    '   └─ Expected number, actual "30"'
}
*/

// 这个输入匹配模式，不会抛出错误
assertsPerson({ name: "Alice", age: 30 })
```

从模式生成的 `assertsPerson` 函数具有以下签名：

```typescript
const assertsPerson: (
  input: unknown,
  overrideOptions?: number | ParseOptions
) => asserts input is {
  readonly name: string
  readonly age: number
}
```

### 管理缺失属性

在解码时，理解缺失属性是如何被处理的是很重要的。默认情况下，如果输入中不存在某个属性，则将其视为存在且值为 `undefined`。

**示例（缺失属性的默认行为）**

```typescript
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.decodeUnknownSync(schema)(input))
// 输出: { a: undefined }
```

在这个例子中，尽管键 `"a"` 在输入中不存在，但默认情况下它被视为 `{ a: undefined }`。

如果你需要验证逻辑来区分真正缺失的属性和显式设置为 `undefined` 的属性，你可以启用 `exact` 选项。

**示例（设置 exact: true 以区分缺失属性）**

```typescript
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.decodeUnknownSync(schema)(input, { exact: true }))
/*
抛出
ParseError: { readonly a: unknown }
└─ ["a"]
   └─ is missing
*/
```

然而，对于 API `Schema.is` 和 `Schema.asserts`，默认行为是严格处理缺失属性，其中 `exact` 的默认值为 `true`：

**示例（Schema.is 和 Schema.asserts 对缺失属性的严格处理）**

```typescript
import type { SchemaAST } from "effect"
import { Schema } from "effect"

const schema = Schema.Struct({ a: Schema.Unknown })
const input = {}

console.log(Schema.is(schema)(input))
// 输出: false

console.log(Schema.is(schema)(input, { exact: false }))
// 输出: true

const asserts: (
  u: unknown,
  overrideOptions?: SchemaAST.ParseOptions
) => asserts u is {
  readonly a: unknown
} = Schema.asserts(schema)

try {
  asserts(input)
  console.log("断言通过")
} catch (e: any) {
  console.error("断言失败")
  console.error(e.message)
}
/*
输出:
断言失败
{ readonly a: unknown }
└─ ["a"]
  └─ is missing
*/

try {
  asserts(input, { exact: false })
  console.log("断言通过")
} catch (e: any) {
  console.error("断言失败")
  console.error(e.message)
}
// 输出: 断言通过
```

### 命名约定

`effect/Schema` 中的命名约定被设计得直观且逻辑清晰，主要关注与 JSON 序列化的兼容性。这种方法简化了对模式的理解和使用，特别是对于集成 Web 技术的开发者来说，JSON 是一种标准的数据交换格式。

#### 命名策略概述

**JSON 兼容类型**

自然地序列化为 JSON 兼容格式的模式直接以其数据类型命名。

例如：

*   `Schema.Date`：将 JavaScript `Date` 对象序列化为 ISO 格式的字符串，这是在 JSON 中表示日期的典型方法。
*   `Schema.Number`：直接使用，因为它精确映射到 JSON 数字类型，无需特殊转换即可保持 JSON 兼容。

**非 JSON 兼容类型**

当处理在 JSON 中没有直接表示的类型时，命名策略会包含额外的细节以指示必要的转换。这有助于对模式的行为建立清晰的预期：

例如：

*   `Schema.DateFromSelf`：表示该模式处理 `Date` 对象，而 `Date` 对象本身不是 JSON 可序列化的。
*   `Schema.NumberFromString`：这个名称表明该模式处理最初表示为字符串的数字，强调了在解码时从字符串到数字的转换。

这些模式的主要目标是确保领域对象可以轻松地序列化（“编码”）和反序列化（“解码”），以便通过网络连接传输，从而促进它们在应用程序的不同部分或不同应用程序之间的传递。

#### 基本原理

虽然 JSON 的普遍性证明了将其作为命名的主要考虑因素是合理的，但这些约定也适应了其他类型传输的序列化。例如，将 `Date` 转换为字符串是一种对各种通信协议（不仅仅是 JSON）都普遍有用的方法。因此，所选的命名约定作为合理的默认值，优先考虑清晰性和易用性，促进了跨不同技术环境的序列化和反序列化过程。
