**Effect Schema 介绍**

欢迎阅读 effect/Schema 的文档，这是一个用于在 TypeScript 中定义和使用模式（schema）来验证和转换数据的模块。

effect/Schema 模块允许你定义一个 `Schema<Type, Encoded, Requirements>`，它提供了一个描述数据结构与数据类型的蓝图。一旦定义好，你就可以利用这个模式来执行一系列操作，包括：

| 操作 | 描述 |
| :--- | :--- |
| **解码** | 将数据从输入类型 `Encoded` 转换为输出类型 `Type`。 |
| **编码** | 将数据从输出类型 `Type` 转换回输入类型 `Encoded`。 |
| **断言** | 验证一个值是否符合模式的输出类型 `Type`。 |
| **标准模式** | 生成一个标准模式 V1（Standard Schema V1）。 |
| **任意值生成** | 为 fast-check 测试生成任意值（arbitraries）。 |
| **JSON 模式** | 基于定义的模式创建 JSON 模式。 |
| **等价性** | 基于定义的模式创建等价性（Equivalence）检查。 |
| **美化打印** | 支持数据结构的美化打印。 |

### 环境要求

*   TypeScript 5.4 或更高版本。
*   在你的 `tsconfig.json` 文件中启用 `strict` 标志。
*   （可选）在你的 `tsconfig.json` 文件中启用 `exactOptionalPropertyTypes` 标志。

```json
{
  "compilerOptions": {
    "strict": true,
    "exactOptionalPropertyTypes": true // 可选
  }
}
```

#### `exactOptionalPropertyTypes` 选项

effect/Schema 模块利用了 `tsconfig.json` 中的 `exactOptionalPropertyTypes` 选项。此选项影响可选属性的类型（要了解有关此选项的更多信息，可以参考 TypeScript 官方文档）。

**示例（启用 `exactOptionalPropertyTypes` 时）**

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.optionalWith(Schema.NonEmptyString, { exact: true })
})

type Type = Schema.Schema.Type<typeof Person>
/*
type Type = {
    readonly name?: string;
}
*/

Schema.decodeSync(Person)({ name: undefined })
// 错误 ts(2379) ― 在启用 'exactOptionalPropertyTypes: true' 的情况下，
// 类型为 '{ name: undefined; }' 的参数不能赋值给类型为 '{ readonly name?: string; }' 的参数。
// 请考虑将 'undefined' 添加到目标属性的类型中。
// 属性 'name' 的类型不兼容。
// 类型 'undefined' 不能赋值给类型 'string'。
```

请注意，这里 `name` 的类型是“精确的”（`string`），这意味着类型检查器会捕获任何尝试赋值无效值（如 `undefined`）的行为。

**示例（禁用 `exactOptionalPropertyTypes` 时）**

如果由于某些原因你无法启用 `exactOptionalPropertyTypes` 选项（可能是因为与其他第三方库冲突），你仍然可以使用 effect/Schema。但是，类型和运行时行为之间会存在不匹配：

```typescript
import { Schema } from "effect"

const Person = Schema.Struct({
  name: Schema.optionalWith(Schema.NonEmptyString, { exact: true })
})

type Type = Schema.Schema.Type<typeof Person>
/*
type Type = {
    readonly name?: string | undefined;
}
*/

// 没有类型错误，但会发生解码失败
Schema.decodeSync(Person)({ name: undefined })
/*
抛出：
ParseError: { readonly name?: NonEmptyString }
└─ ["name"]
   └─ NonEmptyString
      └─ From side refinement failure
         └─ Expected string, actual undefined
*/
```

在这种情况下，`name` 的类型被放宽为 `string | undefined`，这意味着类型检查器不会捕获无效值（`undefined`）。然而，在解码过程中，你会遇到一个错误，表明 `undefined` 是不允许的。

### `Schema` 类型

模式（schema）是一个不可变的值，它描述了你数据的结构，并由 `Schema` 类型表示。

以下是 `Schema` 的一般形式：

```
         ┌─── 解码后的值的类型
         │        ┌─── 编码后的类型（输入/输出）
         │        │      ┌─── 需求（上下文）
         ▼        ▼      ▼
Schema<Type, Encoded, Requirements>
```

`Schema` 类型有三个类型参数，含义如下：

| 参数 | 描述 |
| :--- | :--- |
| **Type** | 表示在解码过程中模式能够成功处理的值的类型。 |
| **Encoded** | 表示在编码过程中模式能够成功处理的值的类型。如果未明确提供，默认等于 `Type`。 |
| **Requirements** | 类似于 `Effect` 类型，它表示模式执行解码和编码所需的上下文数据。如果此类型参数为 `never`（如果未明确提供，则为默认值），则表示该模式没有需求。 |

**示例**

*   `Schema<string>`（默认为 `Schema<string, string, never>`）表示一个解码为 `string`、编码为 `string` 且无需求的模式。
*   `Schema<number, string>`（默认为 `Schema<number, string, never>`）表示一个从 `string` 解码为 `number`、将 `number` 编码为 `string` 且无需求的模式。

#### 类型参数缩写

在 Effect 生态系统中，你经常会看到 `Schema` 的类型参数被缩写为 `A`、`I` 和 `R`。这分别只是 `Type`（类型值 A）、`Input`（输入）和 `Requirements`（需求）的简写。

### 理解 `Schema` 值

*   **不可变性**。`Schema` 值是不可变的，`effect/Schema` 模块中的每个函数都会生成一个新的 `Schema` 值。
*   **建模数据结构**。这些值本身不执行任何操作，它们只是建模或描述数据的结构。
*   **由编译器解释**。一个 `Schema` 可以被各种“编译器”解释为特定的操作，具体取决于编译器类型（解码、编码、美化打印、任意值生成等）。

### 理解解码和编码

在 TypeScript 中处理数据时，你经常需要处理来自外部系统或发送到外部系统的数据。这些数据可能并不总是符合你期望的格式或类型，尤其是在处理用户输入、API 数据或以不同格式存储的数据时。为了处理这些差异，我们使用解码和编码。

| 术语 | 描述 |
| :--- | :--- |
| **解码** | 用于解析来自外部源的数据，这些数据格式你无法控制。 |
| **编码** | 用于将数据发送到外部源时，将其转换为这些源所期望的格式。 |

例如，在前端处理表单时，你经常以字符串的形式接收无类型数据。这些数据可能被篡改，并且本身不支持数组或布尔值。解码帮助你将这些数据验证并解析为更有用的类型，如数字、日期和数组。编码允许你将这些类型转换回表单所期望的字符串格式。

下图展示了使用 `Schema<A, I, R>` 时编码和解码之间的关系：

```
┌─────────┐       ┌───┐       ┌───┐       ┌─────────┐
| unknown |       | A |       | I |       | unknown |
└─────────┘       └───┘       └───┘       └─────────┘
     |              |           |              |
     | validate     |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | is           |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | asserts      |           |              |
     |─────────────►│           |              |
     |              |           |              |
     | encodeUnknown|           |              |
     |─────────────────────────►|              |
                    |           |              |
                    | encode    |              |
                    |──────────►│              |
                    |           |              |
                    |    decode |              |
                    | ◄─────────|              |
                    |           |              |
                    | decodeUnknown|
                    | ◄────────────────────────|
```

我们用一个 `Schema<Date, string, never>` 的例子来分解这些概念。这个模式充当一个工具，用于将 `string` 转换为 `Date`，反之亦然。

#### 编码

当我们谈论“编码”时，我们指的是将 `Date` 更改为 `string` 的过程。简而言之，就是将数据从一种格式转换为另一种格式的行为。

#### 解码

相反，“解码”意味着将 `string` 转换回 `Date`。它本质上是编码的反向操作，数据被恢复为其原始形式。

#### 从 `unknown` 解码

从 `unknown` 解码涉及两个关键步骤：

1.  **检查**：首先，我们验证输入数据（类型为 `unknown`）是否符合预期的结构。在我们的具体例子中，这意味着确保输入确实是一个 `string`。
2.  **解码**：在成功检查之后，我们继续将 `string` 转换为 `Date`。此过程完成了解码操作，其中数据既被验证又被转换。

#### 从 `unknown` 编码

从 `unknown` 编码也涉及两个关键步骤：

1.  **检查**：首先，我们验证输入数据（类型为 `unknown`）是否符合预期的结构。在我们的具体例子中，这意味着确保输入确实是一个 `Date`。
2.  **编码**：在成功检查之后，我们继续将 `Date` 转换为 `string`。此过程完成了编码操作，其中数据既被验证又被转换。

### 模式的规则

使用模式时，有一条重要的规则要记住：你的模式应该以这样的方式构建，即当你同时执行编码和解码操作时，你应该得到原始值。

简而言之，如果你对一个值进行编码，然后立即对其进行解码，结果应该与你开始时的原始值匹配。这条规则确保了你的数据在整个编码和解码过程中保持一致和可靠。

#### 确保一致性

作为一般规则，模式的定义应确保 `encode` + `decode` 返回原始值。
